## 2. Обнаруженные неоднозначности и принятые решения

| Вопрос | Риск | Как обработано в ТЗ |
|---|---|---|
| В v0 указаны вымышленные объекты, цены и даты | Нельзя выводить демо-данные как реальные | Только данные API; макеты — иллюстрации |
| Формат цены неизвестен | Некорректная стоимость за ночь/час | Единица тарифа показывается только после подтверждения контракта |
| Временная модель DateTime не согласована полностью | Сдвиг брони и ошибка интервала | Явная блокирующая задача интеграции, без самовольной конвертации |
| Наличие фронтенд-фильтра не защищает от двойной записи | Конкуренция заявок | Серверная окончательная проверка и обработка `409` |
| Неизвестный исход POST после тайм-аута | Дублирующие бронирования | Не повторять автоматически, проверить фактическое состояние |
| Устаревшие `userId`, `roleId`, `statusId` в исходном UI | Эскалация прав/подмена владельца | Проверить исправленную версию API, серверный авторитет |
| Получены только `src/` файлы Frontend | Не подтверждены версии пакетов и сборка | Запросить manifests/lock, не утверждать, что проект собран |
| Избранное отсутствует в подтверждённом API | Скрытая новая разработка | Вынесено из MVP |

## 3. Что реально проверено и что не проверено

**Проверено:** наличие перечисленных документов и графических файлов; заполненность их разделов; логическое соответствие US/FR/AC; наличие раздельных состояний ошибки/пустых данных; визуальные различия трёх концепций; наличие реальных маршрутов в переданном курсовом Backend и методов клиентского сервисного слоя.

**Не проверено:** работа кнопок прототипов v0; реальная интеграция интерфейса с новым Backend; запуск npm-сборки и E2E-тестов; соответствие интерфейса стандартам WCAG; подтверждение единиц тарифа, временной политики и актуальных прав всех API. Не следует предъявлять проектную документацию как результат этих тестов.

## 4. Вердикт и действия перед разработкой

**Вердикт:** комплект покрывает содержательные требования ДЗ №3. ТЗ структурировано и прослеживается до пользовательских сценариев и критериев приёмки. Его можно сдавать как проектную работу и использовать как основу итеративного редизайна.

**Условия старта реализации:** получить полные конфигурации Frontend, выбрать согласованную версию Backend, сверить DTO/Swagger, решить вопросы времени и тарифа, завершить проверку серверных прав доступа. Это **не недостатки сдаваемых артефактов**, а честно выделенные технические блокеры для будущей реализации.
