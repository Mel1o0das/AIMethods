# Проектирование обработки ошибок и негативных сценариев — BookingService

## 1. Назначение и границы

Документ подготовлен для **шага 5 домашнего задания № 3**: определить, как должен вести себя интерфейс сервиса бронирования бань и глэмпингов при ошибках ввода, отсутствии данных, проблемах сети, отсутствии авторизации и конфликтах бронирований. Результат используется как исходное требование для дальнейшего `technical_specification.md` и редизайна Next.js/React в выбранной концепции № 2 «Премиальный отдых».

Сценарии связаны с 14 историями `US-01`–`US-14` из `user_stories.md` и критериями `AC-xx.y` из `acceptance_criteria.md`. Для **каждой ключевой функции** ниже указаны нормальный исход, негативные ситуации, реакция интерфейса и способ продолжить работу. US-14 (избранное) остаётся за пределами MVP, но граничные случаи для него учтены как резерв на будущее.

**Статус:** это проект UX-поведения, а не отчёт о выполненных E2E-тестах. Макеты v0 не подключены к API. Возможные ошибки сформированы с помощью AI по пользовательским историям, затем сопоставлены с ранее подготовленными критериями и известными особенностями Backend. Пункты, требующие доработки API, обозначены явно.

### На что действительно можно опираться

- В исходном Backend используется `CustomEnvelope` с полями `result`, `error`, `isError`, `timeGenerated` (в JSON с учётом сериализации). `Error.Messages` содержит `Code`, `Message` и необязательный `InvalidField`; интерфейс должен учитывать фактические имена полей в JSON, а не предполагать структуру без проверки.
- Для ошибок приложения `ErrorResult` сопоставляет `VALIDATION → 400`, `AUTHENTICATION → 401`, `AUTHORIZATION → 403`, `NOT_FOUND → 404`, `CONFLICT → 409`, `FAILURE → 500`. При ошибках JWT, прокси или необработанных исключениях ответ может **не** иметь `CustomEnvelope`: обработка не должна падать из-за отсутствия JSON.
- Для бронирований предусмотрены `StartDateTime` и `EndDateTime`; успешная проверка отображаемой доступности ещё не гарантирует успешного сохранения. В ДЗ № 2 реализована дополнительная серверная защита, проверявшаяся отдельными тестами. Подключение именно этой версии Backend к новому Frontend необходимо подтвердить при интеграции.
- Точное правило часовых поясов, единицы тарификации и длительности бронирования по типам объектов ещё требуется согласовать. UI не должен автоматически додумывать такие значения.

## 2. Общие UX-принципы

| Состояние | Что показывает UI | Что разрешено пользователю | Чего нельзя делать |
|---|---|---|---|
| Загрузка данных | Скелетон/индикатор на месте списка, карточки или календаря | Перейти назад; повторить после явной ошибки | Выдавать отсутствие результатов за пустой каталог до получения ответа |
| Пустой корректный ответ | Отдельное пустое состояние с понятным пояснением | Сбросить фильтры, изменить даты, перейти к каталогу | Использовать текст «Ошибка сервера» при HTTP 200 и пустом массиве |
| Ошибка валидации | Ошибка рядом с полем + краткое общее пояснение | Исправить значение без потери заполненной формы | Стирать все данные, показывать только технический код |
| Ошибка чтения (сеть, 5xx) | Сообщение в области контента и кнопка «Повторить» | Повторить безопасный GET-запрос | Бесконечно обновлять данные без контроля, выдавать кэш за актуальный |
| Ошибка записи с достоверным отказом (400/403/409) | Явный отказ и конкретное следующее действие | Исправить ввод, войти, изменить время или обновить объект | Показывать успех или менять статус без подтверждения сервера |
| Ошибка записи с неизвестным результатом (тайм-аут, обрыв) | «Не удалось проверить результат операции» | Проверить актуальное состояние в соответствующем списке | Автоматически повторять POST/PUT без согласованной идемпотентности |
| Нет авторизации — 401 | Предложение войти; сохранение безопасного локального черновика | Войти, затем продолжить доступное действие | Показывать данные предыдущей учётной записи или бесконечно переадресовывать |
| Недостаточно прав — 403 | «Недостаточно прав для этого действия» | Вернуться к разрешённому разделу | Предлагать повторно войти как гарантированное решение или раскрывать закрытые данные |
| Объект отсутствует — 404 | «Объект не найден или больше недоступен» | Вернуться к каталогу / обновить список | Продолжать оформление по удалённой карточке |

**Сохранение состояния:** при исправимых ошибках остаются выбранный объект, начало, окончание, число гостей и комментарий; пароль не сохраняется в черновике. Если выбранный интервал уже занят, его можно оставить видимым для объяснения конфликта, но нельзя считать доступным. Сообщения не должны перекрывать поля или действие на мобильном экране.

**Явность результата:** успешный `200`/`201` подтверждает операцию только после разбора ответа и его согласованной структуры. При тайм-ауте операции записи неизвестно, успел ли сервер выполнить действие; пользователь должен проверить фактическое состояние до повтора. Для формы допускается блокировка кнопки во время запроса, но это не заменяет серверную защиту от двойных бронирований.

## 3. Матрица негативных сценариев по пользовательским историям

В каждой строке приведено проектируемое поведение. `EH-xx.y` — идентификатор сценария ошибок; `US-xx` и `AC-xx.y` — ссылки на соответствующие документы.

**US-01 — Просмотр каталога.** Нормальный сценарий: публичный GET возвращает список, отображаются карточки и пагинация (`AC-01.1`).

|---|---|---|---|
| **EH-01.1** — пустой каталог | Успешный ответ с пустым списком | «Пока нет доступных предложений». Кнопка «Обновить»; не показывать красную ошибку | AC-01.2 |
| **EH-01.2** — каталог не загрузился | Сеть, тайм-аут GET или 5xx | Состояние ошибки вместо карточек: «Не удалось загрузить объекты», кнопка «Повторить»; не подменять данными прототипа | AC-01.3 |
| **EH-01.3** — изображение недоступно | Битая или отсутствующая ссылка на фото | Изображение-заглушка с подписью, остальные данные карточки и кнопка открытия остаются доступны | AC-01.4 |

**US-02 — Фильтрация предложений.** Нормальный сценарий: применённые фильтры и результаты согласованы (`AC-02.1`).

| Сценарий | Причина | UX-реакция и восстановление | Связь |
|---|---|---|---|
| **EH-02.1** — нет подходящих вариантов | Корректно обработанные фильтры дали ноль результатов | «По этим условиям ничего не найдено», видимые выбранные фильтры, «Сбросить фильтры» | AC-02.2 |
| **EH-02.2** — некорректные значения | Отрицательная цена, ноль гостей, неверный формат поля | Ошибка непосредственно под полем; не отправлять неверное значение | AC-02.3 |
| **EH-02.3** — запрос фильтрации не удался | Проблема GET-запроса | Сохранить параметры фильтров, показать «Не удалось обновить результаты» и «Повторить» | AC-02.4 |

**US-03 — Просмотр деталей объекта.** Нормальный сценарий: открывается карточка выбранного объекта (`AC-03.1`).

| Сценарий | Причина | UX-реакция и восстановление | Связь |
|---|---|---|---|
| **EH-03.1** — объекта больше нет | `404` или объект больше не отображается публично | «Объект не найден или больше недоступен», кнопка «К каталогу» | AC-03.2 |
| **EH-03.2** — детали не загрузились | Тайм-аут / 5xx при чтении | Сообщение с «Повторить», не показывать старое содержимое как подтверждённо актуальное | AC-03.3 |
| **EH-03.3** — недостаточно сведений о цене | Неизвестная единица тарифа или сумма | Отображать только подтверждённое API значение; не вычислять предполагаемую итоговую стоимость | AC-03.4 |

**US-04 — Просмотр занятости.** Нормальный сценарий: пользователь видит актуальные на момент ответа занятые интервалы (`AC-04.1`).

| Сценарий | Причина | UX-реакция и восстановление | Связь |
|---|---|---|---|
| **EH-04.1** — занятость не удалось проверить | API availability недоступен, тайм-аут или 5xx | «Не удалось проверить свободное время», кнопка «Повторить»; не помечать неизвестные слоты как свободные | AC-04.2 |
| **EH-04.2** — выбран некорректный диапазон | Начало не раньше окончания | Показать ошибку под полями начала/конца, заблокировать отправку заявки до исправления | AC-04.3 |
| **EH-04.3** — всё занято | Достоверный ответ содержит занятость всего выбранного периода | «На выбранное время нет свободных интервалов», предложить другую дату | AC-04.4 |
| **EH-04.4** — пользователь изменил объект/дату | Старый запрос завершился позже нового | Показывать результат только для актуального выбора; устаревший ответ игнорировать | AC-04.5 |

### 3.2. Авторизация и оформление (гость / пользователь)

**US-05 — Вход и регистрация.** Нормальный сценарий: вход с корректными данными, возврат к сохранённому этапу бронирования (`AC-05.1`).

| Сценарий | Причина | UX-реакция и восстановление | Связь |
|---|---|---|---|
| **EH-05.1** — неверные учётные данные | Ошибка аутентификации | «Не удалось войти. Проверьте электронную почту и пароль», не уточнять, какой именно реквизит неверен | AC-05.2 |
| **EH-05.2** — некорректная форма | Email неверного формата, пароль короче требований, пропущенные поля | Подсветка поля и исправимое сообщение, введённый пароль сохраняется только в текущем контроле ввода до сброса/отправки | AC-05.3 |
| **EH-05.3** — электронная почта занята | Ошибка регистрации существующей учётной записи | «Не удалось зарегистрироваться с этим адресом»; предложить вход; детали сообщения согласовать с политикой приватности | AC-05.4 |
| **EH-05.4** — срок действия токена истёк | `401` от защищённого API | Очистить сведения об авторизованной сессии и чужие данные, показать «Войдите снова»; безопасный черновик можно сохранить | AC-05.5 |

**US-06 — Создание бронирования.** Нормальный сценарий: сервер принимает заявку, UI показывает её созданный идентификатор/статус только после успешного ответа (`AC-06.1`).

| Сценарий | Причина | UX-реакция и восстановление | Связь |
|---|---|---|---|
| **EH-06.1** — интервал занят | `409 Conflict` при создании | «Это время уже занято. Выберите другой интервал», кнопки «Изменить время» / «Проверить занятость», безопасные данные формы сохраняются | AC-06.2 |
| **EH-06.2** — неверные данные заявки | `400`, даты/гости/вместимость | Отобразить ошибки полей; при наличии `error.messages[].invalidField` связать с соответствующим контролом, иначе дать общее сообщение | AC-06.3 |
| **EH-06.3** — пользователь не вошёл | `401` | Предложить вход и затем вернуться к черновику; не показывать успех | AC-06.4 |
| **EH-06.4** — повторное нажатие «Забронировать» | Первый POST в процессе | Заблокировать повторное нажатие и показать индикатор; вторую одновременную отправку с той же формы не делать | AC-06.5 |
| **EH-06.5** — неизвестен результат POST | Тайм-аут/обрыв соединения после отправки | «Не удалось подтвердить результат. Проверьте “Мои бронирования” перед повторной отправкой», ссылка на список; **не** делать автоматический retry POST | AC-06.6 |
| **EH-06.6** — объект стал недоступен | `404` (удалён), `409` (неактивен) — в зависимости от реализации API | Объяснить невозможность создания, предложить «К каталогу», не оставлять активной кнопку бронирования старого объекта | AC-06.7 |

**US-07 — Мои бронирования.** Нормальный сценарий: только собственные заявки и их актуальные статусы (`AC-07.1`).

| Сценарий | Причина | UX-реакция и восстановление | Связь |
|---|---|---|---|
| **EH-07.1** — бронирований нет | Пустой корректный список | «У вас пока нет бронирований», «Посмотреть объекты» | AC-07.2 |
| **EH-07.2** — нет действующей сессии | `401` | Предложить вход, очистить данные предыдущей учётной записи | AC-07.3 |
| **EH-07.3** — не удалось обновить | Сетевой сбой/5xx | «Не удалось обновить бронирования», «Повторить»; если видны кэшированные данные, явно обозначить их неактуальность | AC-07.4 |

**US-08 — Отмена бронирования.** Нормальный сценарий: владелец подтверждает действие, сервер сохраняет статус «Отменено» (`AC-08.1`).

| Сценарий | Причина | UX-реакция и восстановление | Связь |
|---|---|---|---|
| **EH-08.1** — нельзя отменить чужую заявку | `403` | «Недостаточно прав для отмены», оставить статус без изменений, обновить список при необходимости | AC-08.2 |
| **EH-08.2** — переход уже невозможен | Конфликт состояния `409` или иная бизнес-ошибка API | «Статус бронирования изменился. Обновите список», не показывать фиктивную отмену | AC-08.3 |
| **EH-08.3** — результат отмены неизвестен | Обрыв/тайм-аут после запроса | «Не удалось подтвердить отмену. Проверьте актуальный статус», действие «Обновить» | AC-08.4 |
| **EH-08.4** — случайное нажатие | Пользователь нажал «Отменить» | Показать диалог подтверждения; действие «Назад» закрывает его без запроса | AC-08.5 |

### 3.3. Административные операции

**US-09 — Подтверждение заявок.** Нормальный сценарий: администратор подтверждает ожидающую заявку, список актуализируется (`AC-09.1`).

| Сценарий | Причина | UX-реакция и восстановление | Связь |
|---|---|---|---|
| **EH-09.1** — нет полномочий | `403` | «Подтверждение доступно только администратору», не изменять статус в списке | AC-09.2 |
| **EH-09.2** — нет сессии | `401` | Предложить повторный вход; не раскрывать административные данные | AC-09.3 |
| **EH-09.3** — заявка уже отменена | `409` или иной подтверждённый запрет перехода | «Заявку нельзя подтвердить: её статус изменился», «Обновить список» | AC-09.4 |
| **EH-09.4** — неизвестен результат операции | Сетевой сбой после PUT | Оставить «Результат не подтверждён», предложить обновление статуса; без автоматического повторения PUT | AC-09.5 |

**US-10 — Управление объектами.** Нормальный сценарий: корректная запись создаётся/обновляется, новые данные видны в списке (`AC-10.1`).

| Сценарий | Причина | UX-реакция и восстановление | Связь |
|---|---|---|---|
| **EH-10.1** — некорректная форма объекта | `400`, невалидная цена, вместимость, название | Показать ошибки рядом с полями; сохранить введённый текст и ссылки; не сообщать об успешном сохранении | AC-10.2 |
| **EH-10.2** — нет прав | `401` / `403` | При `401` — войти, при `403` — отказ без раскрытия данных; список не менять | AC-10.3 |
| **EH-10.3** — объект скрыт (soft delete) | Успешное скрытие объекта | Убрать его из публичного каталога после подтверждённого ответа; историю бронирований не стирать | AC-10.4 |
| **EH-10.4** — неизвестен результат сохранения | Тайм-аут POST/PUT | Сообщить «Не удалось подтвердить сохранение»; перед повторным созданием проверить список на дубликат | AC-10.5 |

### 3.4. Общие, мобильные и отложенные сценарии

**US-11 — Обработка сбоев.** Нормальный сценарий: пользователь получает ясный исход операции и не видит технических деталей (`AC-11.1`–`AC-11.5`).

| Сценарий | Причина | UX-реакция и восстановление | Связь |
|---|---|---|---|
| **EH-11.1** — ошибки нескольких полей | `400`, `error.messages` | Привязать ошибки к соответствующим полям; не скрывать и не сбрасывать весь черновик | AC-11.1 |
| **EH-11.2** — конфликт | `409` | Сообщить о занятости/изменившемся статусе; предложить правильное действие в текущем контексте | AC-11.2 |
| **EH-11.3** — доступ запрещён | `401` / `403` | Разделять вход и отсутствие прав; скрытые данные не отображать | AC-11.3 |
| **EH-11.4** — ответ на запись потерян | Сеть, тайм-аут, разрыв | Не делать автоматическую повторную отправку, дать проверку фактического результата | AC-11.4 |
| **EH-11.5** — ошибка сервера или некорректный ответ | `500`, нестандартный JSON, пустое тело ошибки | «Что-то пошло не так. Попробуйте позже» + «Повторить» для чтения; не выводить SQL, стек-трейс, JWT или сырые ошибки | AC-11.5 |

**US-12 — Мобильные фильтры.** Нормальный сценарий: фильтры доступны на узком экране (`AC-12.1`).

| Сценарий | Причина | UX-реакция и восстановление | Связь |
|---|---|---|---|
| **EH-12.1** — панель закрыта без применения | Пользователь передумал | Сохранить согласованное состояние и не отправлять запрос случайно | AC-12.2 |
| **EH-12.2** — фильтры дали пустой список | Выбранное сочетание недоступно | В панели и над каталогом видно активные параметры; есть «Сбросить» | AC-12.3 |
| **EH-12.3** — клавиатурный пользователь не может закрыть панель | Недоработанное модальное управление | Кнопка закрытия и Escape работают, фокус возвращается на кнопку «Фильтры» | AC-12.4 |

**US-13 — Выбор интервала по типу объекта.** Нормальный сценарий: баня — сеанс с временем, глэмпинг — период проживания; обе формы формируют совместимые `StartDateTime`/`EndDateTime` (`AC-13.1`–`AC-13.2`).

| Сценарий | Причина | UX-реакция и восстановление | Связь |
|---|---|---|---|
| **EH-13.1** — окончание раньше/равно началу | Неправильно выбранные границы | Подсветка пары полей и текст «Окончание должно быть позже начала»; не отправлять | AC-13.3 |
| **EH-13.2** — неизвестна тарификация | API не передаёт единицу цены или правила расчёта | «Итоговая стоимость уточняется»; нельзя показывать рассчитанную наугад сумму | AC-13.4 |
| **EH-13.3** — время неоднозначно | Несогласованные UTC/локальное время, переход часов | Не выполнять скрытую конвертацию; показать выбранные значения и остановить оформление, пока не согласован контракт | AC-13.1–AC-13.4; открытый вопрос |

**US-14 — Избранное (вне MVP).** Нормальный сценарий описан в `AC-14.1` и `AC-14.2`, но в текущую реализацию не включается.

| Сценарий | Причина | UX-реакция и восстановление | Связь |
|---|---|---|---|
| **EH-14.1** — пользователь не авторизован | Попытка добавить в избранное без JWT | После включения функции предложить вход без утверждения об успешном сохранении | AC-14.3 |
| **EH-14.2** — сохранение не удалось | Сеть / сервер / недоступное хранилище | Не показывать устойчивую отметку «В избранном», предложить безопасную проверку/повтор после выяснения состояния | AC-14.4 |

## 4. Тексты сообщений для интерфейса

Тексты являются предлагаемыми макетными формулировками. Точная локализация и оформление будут проверяться при разработке Frontend.

| Ситуация | Заголовок/сообщение пользователю | Основное действие |
|---|---|---|
| Список пуст | «Пока нет доступных предложений» | «Обновить» |
| Фильтры ничего не нашли | «По выбранным условиям ничего не найдено» | «Сбросить фильтры» |
| GET не загрузился | «Не удалось загрузить данные. Проверьте соединение» | «Повторить» |
| Занятость неизвестна | «Сейчас не удаётся проверить свободное время» | «Проверить снова» |
| Интервал занят (`409`) | «Это время уже занято. Выберите другое» | «Изменить время» |
| Начало после окончания | «Окончание должно быть позже начала» | Исправить даты |
| Число гостей превышает вместимость | «Количество гостей превышает вместимость объекта» | Изменить число гостей |
| Неверные данные входа | «Не удалось войти. Проверьте данные» | «Попробовать снова» |
| Сессия истекла (`401`) | «Сессия завершилась. Войдите снова» | «Войти» |
| Недостаточно прав (`403`) | «Недостаточно прав для этого действия» | «Вернуться» |
| Объект не найден (`404`) | «Объект не найден или больше недоступен» | «К каталогу» |
| Тайм-аут после POST | «Не удалось подтвердить создание заявки. Проверьте свои бронирования перед повторной отправкой» | «Мои бронирования» |
| Тайм-аут после отмены | «Не удалось подтвердить отмену. Проверьте статус заявки» | «Обновить статус» |
| Серверная ошибка (`500`) | «Сервис временно недоступен. Попробуйте позже» | «Повторить» для GET; «Проверить статус» для записи |

Всплывающее уведомление (`notification`/`message` Ant Design) подходит для краткого результата, но **критические ошибки форм и действий не должны существовать только в исчезающем toast**. Для них требуется постоянный текст у поля или в блоке состояния формы. Нельзя включать в пользовательский текст исходную строку подключения, исключение, токен или персональные данные других гостей.

## 5. Логика обработки HTTP и запросов

1. **200/201 с корректным результатом:** обновить UI. Пустой результат GET — это отдельное состояние, а не ошибка сети. Для операций записи проверить контракт и получить подтверждение.
2. **400:** прочитать `error.messages`, показать относящиеся к полям ошибки и сохранить черновик. Если структура ответа отличается, показать общее безопасное сообщение.
3. **401:** удалить из клиентского состояния сведения о текущей сессии и приватные данные, предложить вход. Не повторять один и тот же защищённый запрос по кругу.
4. **403:** сообщить о недостатке полномочий; не раскрывать данные и не запускать требующее привилегий действие снова автоматически.
5. **404:** для GET открыть пустое состояние объекта, для отмены/подтверждения предложить обновить список; не работать с устаревшим идентификатором.
6. **409:** в зависимости от контекста — занятый интервал, недоступный объект или недопустимый переход статуса. Не подменять все конфликты текстом «Время занято».
7. **500/502/503 или сбой разбора ответа:** показать безопасное сообщение; детали — в технических логах без секретов. Сетевые ошибки не имеют обязательного HTTP-статуса.
8. **Тайм-аут:** отличать чтение от записи. GET можно запустить повторно по действию пользователя; POST/PUT/DELETE нельзя автоматически повторять без доказанной идемпотентности и проверки результата.
9. **Смена фильтра/объекта/даты во время GET:** отменять либо игнорировать устаревшие ответы, чтобы не отобразить занятость другого объекта.
10. **Согласованность авторизации:** при смене пользователя очистить кэш личных бронирований и администраторских данных; простое сокрытие кнопки не заменяет проверку прав на API.

### Рекомендуемые состояния компонентов

| Компонент | Состояния для UI | Проверка корректности |
|---|---|---|
| Каталог | initial / loading / success / empty / error | При ошибке сеть ≠ пустой список |
| Фильтры | idle / applying / applied / invalid / error | Активные параметры остаются видны |
| Детали объекта | loading / ready / not-found / error | Не разрешать бронировать удалённый объект |
| Календарь | loading / available / occupied / unknown / error | `unknown` не означает «свободно» |
| Бронирование | draft / validating / submitting / success / rejected / unknown-result | Тайм-аут POST ≠ гарантированный отказ |
| Вход | idle / submitting / invalid / unauthorized / success | Не раскрывать, существует ли email |
| Отмена/подтверждение | idle / confirming / pending / success / rejected / unknown-result | Менять финальный статус лишь при подтверждении сервера |

## 7. Правила доступности и оформления ошибок

- В тёмной концепции № 2 сообщения должны иметь контраст с фоном; красный цвет не является единственным способом обозначить ошибку (нужны текст и, при необходимости, иконка).
- Ошибка поля располагается под соответствующим элементом формы. Для экранных дикторов используется ассоциация поля с ошибкой (например, `aria-describedby`), фокус переводится на первое ошибочное поле после неудачной отправки.
- Изменения статуса и ошибки объявляются доступным образом (`role="alert"` или `aria-live` по смыслу), не заставляя пользователя догадываться по анимации.
- На экране телефона шириной порядка 375–430 CSS px сообщения и кнопки должны оставаться доступны без горизонтальной прокрутки.
- Нельзя полагаться на демонстрационные фотографии, тестовые статусы или заранее заданные цены макета: источник истины — подключённый API.

## 8. Открытые вопросы и ограничения

1. **Часовые пояса.** Нужно определить, как Frontend сериализует дату и время и как Backend их интерпретирует; особенно для бань с почасовой арендой.
2. **Тарифы.** Единица цены и расчёт итоговой суммы не должны угадываться: UI должен показывать сумму только при согласованном контракте.
3. **Повторная запись.** Нет подтверждения общего механизма идемпотентности для создания и изменения бронирований. Пока безопасный UX — проверить фактическое состояние после тайм-аута.
4. **Коды бизнес-ошибок.** Перед реализацией нужно сверить конкретные `error.messages[].code` и `invalidField` с актуальной версией Backend (в частности после ДЗ № 2). Нельзя полагаться только на русское сообщение.
5. **Регистрация и роли.** Сервер обязан сам ограничивать назначение роли и владение бронированиями; скрытие административной панели на Frontend не обеспечивает безопасность.
6. **Проектный объём.** US-14 «Избранное» — вне MVP; для него в текущем API не подтверждено хранение данных.
7. **Статус тестирования.** Матрица и кейсы служат требованиями к будущей реализации. Для v0-прототипов интеграционные проверки ошибок не проводились.
