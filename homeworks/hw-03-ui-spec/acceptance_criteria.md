# Критерии приёмки (Acceptance Criteria) — BookingService

## 1. Назначение

Документ уточняет **все 14 User Stories** из `user_stories.md` для редизайна сервиса бронирования бань и глэмпингов. Визуальное направление — концепция №2 «Премиальный отдых», дополненная поиском и более информативным каталогом. Формулировки ниже — **требования к целевому поведению и сценарии будущей проверки**, а не отчёт о выполненных UI-тестах.

Каждый критерий помечен номером `AC-xx.y`, связан с исходной историей `US-xx` и записан как **Given (условие) — When (действие) — Then (проверяемый результат)**. Метки «Позитивный», «Граничный», «Ошибка» помогают составить тест-план. Проверка выполняется на согласованной версии Frontend и Backend, а не на статических макетах v0.

Учитываются следующие существующие сведения: сервер использует `StartDateTime`/`EndDateTime`; занятость интервалов рассчитывается по полуоткрытой модели `[start, end)`; созданные заявки начинают со статуса «Ожидает подтверждения» в доработанном Backend ДЗ №2; конфликт бронирований выражается ответом `409 Conflict`. Для нового UI обязательно проверить совместимость с конкретной версией API и фактическими названиями статусов в тестовой БД.

**Границы документа.** Внешнее поведение, которое не подтверждено исходниками, сформулировано как проектное требование. Правила часовых поясов, длительности посещения и единиц тарификации необходимо согласовать отдельно. US-14 (избранное) не входит в MVP.

## 3. Детальные сценарии Given–When–Then

Для приемки критерия требуется не только ожидаемый текст уведомления, но и проверяемое состояние интерфейса и, где уместно, факт сохранения (или отсутствия изменения) в Backend. Результат запроса нельзя угадывать по демонстрационным данным в прототипе.

### US-01. Просмотр каталога

**Приоритет:** Must have. **Источник:** `US-01` в `user_stories.md`.

- **AC-01.1 (Позитивный).** **Given** гость открывает каталог и API возвращает хотя бы один доступный для показа объект; **When** данные загружаются; **Then** появляются карточки с названием, фотографией или резервным изображением, ценой с единицей тарифа (если она известна API) и вместимостью; вход не требуется.
- **AC-01.2 (Пустые данные).** **Given** API возвращает пустую страницу каталога; **When** завершается загрузка; **Then** показываются сообщение «Пока нет доступных объектов» и возможность обновить список или изменить фильтры; пустой экран не допускается.
- **AC-01.3 (Состояние загрузки).** **Given** запрос каталога ещё не завершён; **When** открывается экран каталога; **Then** видно обозначенное состояние загрузки, а интерфейс не отображает предыдущие данные как новые.
- **AC-01.4 (Ошибка сети).** **Given** запрос каталога не удался из-за сетевого сбоя; **When** запрос завершился ошибкой; **Then** появляется сообщение о невозможности загрузить объекты и действие «Повторить»; фиктивные результаты не выводятся.

### US-02. Фильтрация предложений

**Приоритет:** Must have. **Источник:** `US-02` в `user_stories.md`.

- **AC-02.1 (Позитивный).** **Given** в каталоге есть объекты разных типов, стоимости и вместимости; **When** гость выбирает тип, верхний предел цены и минимальную вместимость; **Then** список содержит только подходящие объекты и выбранные значения явно показаны в элементах управления.
- **AC-02.2 (Пустые данные).** **Given** выбраны условия, которым не соответствует ни один объект; **When** фильтры применяются; **Then** показывается сообщение «Ничего не найдено» и доступна кнопка сброса фильтров.
- **AC-02.3 (Граничный).** **Given** установлены фильтры и пользователь нажимает «Сбросить»; **When** сброс выполнен; **Then** поля возвращаются к значениям по умолчанию, а результаты снова запрашиваются или пересчитываются без старых ограничений.
- **AC-02.4 (Согласованность).** **Given** после фильтрации пользователь находился не на первой странице списка; **When** условие фильтра изменяется; **Then** отображается первая корректная страница новой выборки; старый номер страницы не приводит к ложному пустому результату.
- **AC-02.5 (Ошибка сети).** **Given** фильтры требуют запроса к серверу и он завершился ошибкой; **When** гость применяет фильтр; **Then** приложение сообщает о сбое и сохраняет выбранные значения для повторной попытки.

### US-03. Просмотр деталей объекта

**Приоритет:** Must have. **Источник:** `US-03` в `user_stories.md`.

- **AC-03.1 (Позитивный).** **Given** карточка объекта присутствует в каталоге; **When** гость открывает её; **Then** отображаются данные именно выбранного объекта, описание, вместимость, цена с известной единицей тарифа и действие «Забронировать», если объект доступен.
- **AC-03.2 (Не найдено).** **Given** сервер сообщает, что объект отсутствует или удалён (`404`); **When** гость открывает его прежнюю ссылку; **Then** появляется понятное сообщение и переход обратно к каталогу; форма бронирования не открывается.
- **AC-03.3 (Недоступный объект).** **Given** сервер отмечает объект как неактивный; **When** отображается карточка или подробности; **Then** интерфейс явно сообщает «Сейчас недоступен» и не предлагает отправить бронирование.
- **AC-03.4 (Навигация).** **Given** пользователь открыл детали из каталога с установленными фильтрами; **When** закрывает карточку или возвращается назад; **Then** отображается каталог без неожиданной потери выбранных фильтров и контекста поиска.

### US-04. Проверка занятого времени

**Приоритет:** Must have. **Источник:** `US-04` в `user_stories.md`.

- **AC-04.1 (Позитивный).** **Given** для выбранного объекта сервис доступности вернул занятые интервалы; **When** открывается календарь/выбор времени; **Then** занятые промежутки отличимы от свободных и не предлагаются как доступный вариант бронирования.
- **AC-04.2 (Граница интервала).** **Given** существующая запись занимает `[10:00, 12:00)`, а новая начинается в `12:00`; **When** пользователь выбирает следующий интервал; **Then** пользователь может выбрать интервал при прочих допустимых условиях: соприкосновение без пересечения не считается конфликтом.
- **AC-04.3 (Ошибка сети).** **Given** сервис доступности не ответил; **When** пользователь открыл выбор времени; **Then** появляются сообщение об ошибке и «Повторить»; неизвестная доступность не помечается как свободная.
- **AC-04.4 (Устаревший ответ).** **Given** пользователь сменил объект или диапазон до завершения прежнего запроса; **When** приходит запоздавший ответ для прошлого выбора; **Then** интервалы предыдущего объекта/диапазона не отображаются как актуальные для нового выбора.
- **AC-04.5 (Конкурентность).** **Given** интервал показан свободным, но занят другим пользователем до сохранения; **When** клиент отправляет заявку; **Then** клиент принимает окончательное решение сервера; предварительный ответ availability не переопределяет `409 Conflict`.

### US-05. Вход и регистрация

**Приоритет:** Must have. **Источник:** `US-05` в `user_stories.md`.

- **AC-05.1 (Позитивный).** **Given** гость ввёл корректные данные существующей учётной записи; **When** отправляет форму входа; **Then** после ответа сервера интерфейс отображает авторизованное состояние и предоставляет возможность продолжить бронирование.
- **AC-05.2 (Неверные данные).** **Given** пользователь ввёл неверный пароль; **When** отправляет форму входа; **Then** показывается нейтральная ошибка аутентификации без уточнения, существует ли указанный email.
- **AC-05.3 (Невалидная регистрация).** **Given** при регистрации обязательное поле отсутствует или пароль не соответствует правилам сервера; **When** пользователь отправляет форму; **Then** создание учётной записи не считается успешным; показываются корректируемые ошибки.
- **AC-05.4 (Переход из бронирования).** **Given** гость сформировал допустимый черновик заявки, но ещё не вошёл в систему; **When** нажимает «Забронировать»; **Then** его направляют ко входу; после успешной авторизации выбранный объект, даты и количество гостей сохраняются в черновике текущей сессии, а доступность повторно проверяется перед отправкой.
- **AC-05.5 (Ошибка сети).** **Given** запрос входа или регистрации завершился сетевой ошибкой; **When** ожидается результат; **Then** приложение не показывает успешный вход без подтверждения API и предлагает повторить действие.

### US-06. Создание бронирования

**Приоритет:** Must have. **Источник:** `US-06` в `user_stories.md`.

- **AC-06.1 (Позитивный).** **Given** пользователь вошёл, объект активен, гостей не больше вместимости и интервал свободен; **When** отправляет заполненную корректную форму; **Then** API создаёт заявку, UI показывает подтверждение и начальный статус «Ожидает подтверждения» после фактического успешного ответа.
- **AC-06.2 (Конфликт).** **Given** за время заполнения слот заняли другим бронированием; **When** POST возвращает `409 Conflict`; **Then** интерфейс не показывает успех, объясняет занятость и предлагает выбрать другой интервал, сохраняя безопасные поля черновика.
- **AC-06.3 (Валидация).** **Given** конец интервала не позже начала, число гостей не положительно или превышает вместимость; **When** форма отправляется или проверяется перед отправкой; **Then** показываются причины некорректности; заявка не подтверждается как созданная.
- **AC-06.4 (Авторизация).** **Given** у пользователя нет действующей сессии; **When** он пытается создать заявку; **Then** защищённый API возвращает `401`, интерфейс предлагает войти и не утверждает, что заявка оформлена.
- **AC-06.5 (Повторное нажатие).** **Given** отправка бронирования уже выполняется; **When** пользователь повторно нажимает кнопку; **Then** вторая одновременная отправка с этой формы не выполняется; кнопка имеет состояние ожидания.
- **AC-06.6 (Неизвестный результат).** **Given** после отправки произошёл тайм-аут или разрыв соединения; **When** клиент не получил ответ; **Then** экран не заявляет, что бронирования точно нет, и предлагает проверить «Мои бронирования» перед новой отправкой.
- **AC-06.7 (Неактивный объект).** **Given** объект стал неактивным или удалённым до оформления; **When** сервер отклоняет создание; **Then** клиент показывает причину невозможности бронирования и даёт вернуться к каталогу.

### US-07. Просмотр своих бронирований

**Приоритет:** Must have. **Источник:** `US-07` в `user_stories.md`.

- **AC-07.1 (Позитивный).** **Given** зарегистрированный пользователь имеет две собственные заявки; **When** открывает «Мои бронирования»; **Then** видит только свои заявки с объектом, временем начала/конца и актуальным статусом.
- **AC-07.2 (Пустые данные).** **Given** для пользователя нет бронирований; **When** открывается список; **Then** отображается «У вас пока нет бронирований» и переход к каталогу.
- **AC-07.3 (Авторизация).** **Given** сессия отсутствует или истекла; **When** запрашивается список; **Then** API отвечает `401`; интерфейс предлагает повторный вход и не показывает данные предыдущего пользователя.
- **AC-07.4 (Ошибка сети).** **Given** сервер временно недоступен; **When** пользователь обновляет список; **Then** показывается сообщение о невозможности обновления и действие «Повторить», без выдачи устаревшего статуса за подтверждённо актуальный.

### US-08. Отмена своей заявки

**Приоритет:** Must have. **Источник:** `US-08` в `user_stories.md`.

- **AC-08.1 (Позитивный).** **Given** пользователь владеет заявкой и её текущий статус допускает отмену; **When** подтверждает отмену; **Then** сервер сохраняет статус «Отменено», экран обновляется и действие отмены больше не доступно.
- **AC-08.2 (Чужая заявка).** **Given** обычный пользователь пытается отменить бронирование другого человека; **When** отправляет запрос; **Then** API возвращает `403`, чужая заявка не меняется, UI отображает отказ без успеха.
- **AC-08.3 (Недопустимый переход).** **Given** сервер отклоняет отмену текущего статуса; **When** приходит ошибка перехода состояния; **Then** UI оставляет старый статус и предлагает обновить данные вместо фиктивной отмены.
- **AC-08.4 (Ошибка сети).** **Given** после запроса отмены ответа не получено; **When** завершается ожидание по тайм-ауту; **Then** UI не утверждает, что бронь отменена, и предлагает обновить фактический статус.
- **AC-08.5 (Подтверждение действия).** **Given** владелец нажал «Отменить» по ошибке; **When** появляется диалог подтверждения; **Then** операция не отправляется до отдельного подтверждения; действие «Назад» закрывает диалог без изменений.

### US-09. Подтверждение заявок администратором

**Приоритет:** Must have. **Источник:** `US-09` в `user_stories.md`.

- **AC-09.1 (Позитивный).** **Given** администратор вошёл и есть заявка «Ожидает подтверждения»; **When** администратор подтверждает заявку и сервер успешно отвечает; **Then** заявка отображается со статусом «Подтверждено», а список актуализируется.
- **AC-09.2 (Недостаточно прав).** **Given** запрос отправляет обычный пользователь; **When** пытается подтвердить бронирование; **Then** сервер отвечает `403`, статус бронирования не изменяется.
- **AC-09.3 (Нет авторизации).** **Given** запрос отправляется без действующего JWT; **When** вызывается административная операция; **Then** сервер отвечает `401`, интерфейс предлагает войти.
- **AC-09.4 (Недопустимый переход).** **Given** администратор пытается подтвердить отменённую заявку; **When** сервер проверяет изменение статуса; **Then** возвращается конфликт состояния, UI сообщает об этом и не показывает успех.
- **AC-09.5 (Ошибка сети).** **Given** подтверждение отправлено, но ответ не получен; **When** истекает ожидание; **Then** UI предлагает получить актуальный статус до повторной отправки, без оптимистического финального подтверждения.

### US-10. Управление объектами

**Приоритет:** Must have. **Источник:** `US-10` в `user_stories.md`.

- **AC-10.1 (Позитивный).** **Given** авторизованный администратор ввёл корректные сведения об объекте; **When** нажимает «Сохранить» и сервер возвращает успех; **Then** созданная либо обновлённая запись видна в административном списке с актуальными данными.
- **AC-10.2 (Ошибки формы).** **Given** в обязательном поле нет допустимого значения или цена/вместимость не проходят серверную валидацию; **When** администратор сохраняет объект; **Then** показываются конкретные ошибки у соответствующих полей, успешное сохранение не имитируется.
- **AC-10.3 (Нет прав).** **Given** обычный пользователь пытается создать либо изменить объект; **When** обращается к защищённой операции; **Then** API возвращает `403` и данные объекта остаются неизменными.
- **AC-10.4 (Мягкое удаление).** **Given** администратор скрывает объект доступным штатным действием; **When** операция прошла успешно; **Then** объект исключается из публичной выдачи согласно серверным правилам; исторические бронирования не удаляются.
- **AC-10.5 (Ошибка сети).** **Given** ответ на сохранение не пришёл; **When** администратор видит завершение ожидания; **Then** интерфейс сообщает о неопределённом результате и предлагает обновить список перед повторным созданием.

### US-11. Понятные сообщения о сбоях

**Приоритет:** Must have. **Источник:** `US-11` в `user_stories.md`.

- **AC-11.1 (Ошибка валидации).** **Given** API создания бронирования возвращает `400` с ошибками входных данных; **When** форма получает ответ; **Then** UI показывает исправляемые ошибки и не стирает введённые объект, даты, гостей и комментарий.
- **AC-11.2 (Конфликт).** **Given** API возвращает `409 Conflict` на занятый интервал; **When** пользователь видит ответ; **Then** UI предлагает изменить время и повторно проверить доступность, не выдавая сообщение об успешной заявке.
- **AC-11.3 (Нет прав).** **Given** API возвращает `401` или `403`; **When** обрабатывается ответ; **Then** при `401` предлагается вход, при `403` показывается отсутствие прав без раскрытия закрытых данных.
- **AC-11.4 (Сетевой сбой).** **Given** POST мог дойти до сервера, но ответ потерян; **When** истекает время ожидания; **Then** UI сообщает, что результат неизвестен, и предлагает проверить свои заявки; автоматическая повторная отправка без механизма идемпотентности не выполняется.
- **AC-11.5 (Сбой сервера).** **Given** API возвращает `500` либо другой необработанный сбой; **When** интерфейс показывает результат; **Then** пользователь видит общее сообщение без SQL, стек-трейсов, токенов и конфиденциальных деталей.

### US-12. Фильтры на мобильном экране

**Приоритет:** Should have. **Источник:** `US-12` в `user_stories.md`.

- **AC-12.1 (Позитивный).** **Given** каталог открыт на мобильном экране шириной около 375–430 CSS-пикселей; **When** гость открывает панель фильтров; **Then** тип, цена и вместимость доступны без горизонтальной прокрутки страницы.
- **AC-12.2 (Сохранение состояния).** **Given** пользователь выбрал фильтры на мобильном устройстве; **When** закрывает панель и возвращается к каталогу; **Then** выбранные значения и соответствующая выборка сохраняются.
- **AC-12.3 (Сброс).** **Given** панель содержит несколько активных фильтров; **When** пользователь нажимает «Сбросить»; **Then** контролы возвращаются к состоянию по умолчанию и видимая выборка обновляется.
- **AC-12.4 (Доступность управления).** **Given** панель фильтров открыта; **When** пользователь нажимает Escape или явную кнопку закрытия; **Then** панель закрывается без случайной отправки формы; фокус возвращается к кнопке открытия при работе с клавиатурой.

### US-13. Выбор интервала по типу объекта

**Приоритет:** Should have. **Источник:** `US-13` в `user_stories.md`.

- **AC-13.1 (Позитивный).** **Given** выбрана баня и серверный контракт поддерживает временные интервалы; **When** пользователь открывает форму; **Then** видит отдельные поля начала и окончания посещения с понятным форматом даты и времени.
- **AC-13.2 (Позитивный).** **Given** выбран глэмпинг и согласованы правила периода проживания; **When** пользователь открывает форму; **Then** видит понятные поля начала и окончания проживания; значения передаются в действующие `StartDateTime`/`EndDateTime` без скрытого изменения часового пояса.
- **AC-13.3 (Ошибка валидации).** **Given** окончание интервала не позже начала; **When** пользователь продолжает оформление; **Then** форма сообщает, что окончание должно быть позже начала, и не подтверждает корректность интервала.
- **AC-13.4 (Отсутствующие тарифные сведения).** **Given** API не сообщает согласованную единицу тарифа или достаточные данные для вычисления итоговой стоимости; **When** пользователь просматривает форму выбранного объекта; **Then** UI не показывает рассчитанную наугад итоговую сумму, а объясняет, что окончательная стоимость пока не определена.

### US-14. Избранные объекты

**Приоритет:** Nice to have, вне MVP. **Источник:** `US-14` в `user_stories.md`.

- **AC-14.1 (Позитивный).** **Given** авторизованный пользователь видит доступный объект и функция избранного реализована; **When** нажимает «В избранное»; **Then** объект сохраняется в персональном списке и отображается как отмеченный.
- **AC-14.2 (Повторный просмотр).** **Given** объект уже находится в избранном пользователя; **When** пользователь возвращается к карточке; **Then** значок сохранённого объекта отображает действительное состояние из данных пользователя.
- **AC-14.3 (Авторизация).** **Given** неавторизованный гость нажимает «В избранное»; **When** приложение обрабатывает действие; **Then** гостю предлагается войти; персональные данные не сохраняются за анонимным пользователем без явно согласованного режима.
- **AC-14.4 (Удаление из избранного).** **Given** пользователь удаляет объект из своего списка избранного; **When** сервер подтверждает действие; **Then** объект исчезает из личного списка, а состояние кнопки на карточке обновляется.

## 4. Общие правила приёмки

1. **Достоверность:** успех создания, отмены, подтверждения и редактирования показывается только после подтверждения сервера. При сетевом тайм-ауте после изменяющего запроса результат считается неизвестным, а не автоматически неудачным.
2. **Авторизация:** UI не заменяет проверку на сервере. Отсутствие кнопки у гостя не считается подтверждением безопасности; API должен возвращать ожидаемые `401` или `403`.
3. **Доступность:** ответ запроса свободного времени — предварительная информация. Окончательная проверка происходит при создании бронирования; конфликт должен обрабатываться независимо от ранее показанного календаря.
4. **Сохранность ввода:** при исправимой ошибке не теряются корректно заполненные поля формы. Пароль и токен при этом не выводятся в сообщения или логи.
5. **Адаптация:** проверяются как минимум настольное представление и мобильный диапазон около 375–430 CSS-пикселей. Это требование к будущему тестированию, а не результат уже проведённых замеров.
6. **Права и персональные данные:** список «Мои бронирования» должен быть ограничен текущим пользователем. Ни URL, ни переданный с клиента идентификатор другого пользователя не могут дать доступ к его данным.

## 5. Тестовые наборы для будущей проверки

- **Каталог:** непустая выдача; пустой каталог; фильтр без совпадений; ошибка загрузки; изменение фильтра при пагинации.
- **Интервалы:** полный и частичный конфликт; соприкосновение без наложения; смена объекта до завершения запроса; пропажа соединения.
- **Создание:** свободный интервал; `400`; `401`; `409`; двойное нажатие; потеря ответа после POST.
- **Личный кабинет и роли:** собственные данные; чужие данные; `401`; `403`; допустимый и запрещённый переход статуса.
- **Администрирование:** корректное создание/редактирование объекта; ошибки ввода; мягкое удаление; потеря ответа на сохранение.
- **Мобильный интерфейс:** каталог и фильтры на узком экране; управление кнопками и клавиатурой; сохранение введённых параметров.

## 6. Открытые вопросы перед разработкой

1. В какой временной зоне Backend принимает и хранит интервалы и как определяется локальная зона объекта? Нельзя молча конвертировать неопределённое `DateTime` в UTC.
2. Какая единица тарификации используется для разных типов объекта и должен ли Frontend вообще рассчитывать итоговую стоимость? Из демонстрационных макетов это не следует.
3. Нужны ли для глэмпингов строго посуточные бронирования, а для бань — минимальная длительность и фиксированный шаг времени? Действующая модель API хранит общий интервал и не задаёт всех таких правил.
4. Как API обозначает статус неактивного, удалённого и временно недоступного объекта; какие коды ответа окончательно согласованы?
5. Какой способ проверки уже отправленной заявки доступен при тайм-ауте POST? Пока безопасное минимальное действие — открыть «Мои бронирования», без автоматического повтора.
6. Должна ли текущая страница объекта быть отдельным маршрутом или модальным окном? В исходных материалах встречаются оба варианта; критерии не требуют менять способ навигации без отдельного решения.

Эти вопросы не следует скрывать в ТЗ. В итоговом `technical_specification.md` их нужно перечислить как условия, требующие решения до реализации соответствующих функций.
