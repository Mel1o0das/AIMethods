Главное архитектурное решение: для текущей модели рекомендую транзакционную блокировку строки `BookingObject` с проверкой пересечения и вставкой в одной транзакции. Она требует меньше изменений, чем exclusion constraint, и корректно работает с текущим правилом «все статусы, кроме отменённого, блокируют интервал».

Exclusion constraint надёжнее как независимая гарантия БД, но в текущей схеме его нельзя корректно отфильтровать по имени статуса из связанной таблицы без денормализации признака блокировки.

## 1. Сравнение вариантов реализации

| Критерий | PostgreSQL exclusion constraint | Блокировка `BookingObject` |
|---|---|---|
| Защита от параллельных запросов | Максимальная, обеспечивается БД | Надёжная при соблюдении протокола всеми путями записи |
| Защита от прямых SQL-вставок | Да | Нет |
| Поддержка полуоткрытого интервала | Нативно через `tstzrange(..., '[)')` | Через SQL-условие |
| Работа с динамическими статусами | Проблематична | Естественная |
| Изменение текущей модели | Потребуется денормализация или переработка статусов | Минимальное |
| Реализация через EF Core | Миграция с raw SQL, обработка PostgreSQL constraint violation | EF-транзакция и параметризованный `SELECT ... FOR UPDATE` |
| Конкурентность | Очень высокая | Запросы сериализуются только в пределах одного объекта |
| Риск неправильного обхода | Низкий | Все create/confirm/update пути обязаны брать блокировку |
| Сложность эксплуатации | Нужны GiST, `btree_gist`, понятная модель блокирующих записей | Нужен контроль времени ожидания блокировки и транзакционных границ |

### Ограничение exclusion constraint в текущей модели

Желаемое ограничение выглядело бы примерно так:

```sql
EXCLUDE USING gist
(
    booking_object_id WITH =,
    tstzrange(start_date_time, end_date_time, '[)') WITH &&
)
WHERE (blocks_availability);
```

Но сейчас `blocks_availability` отсутствует. Бронирование хранит только `status_id`, а признак отмены определяется именем строки в `booking_statuses`.

Predicate частичного ограничения не может выполнять join к `booking_statuses`. Возможные обходы:

- хранить `blocks_availability` непосредственно в `bookings`;
- хранить `cancelled_at` и применять ограничение к `cancelled_at IS NULL`;
- использовать фиксированный UUID отменённого статуса в миграции;
- запрещать пересечения независимо от статуса.

Первые два варианта дублируют состояние, третий связывает схему с конкретными данными, четвёртый ломает отмену и повторное использование интервала.

## 2. Выбранный механизм и обоснование

### Основной механизм

В одной транзакции:

1. Заблокировать строку объекта через `SELECT ... FOR UPDATE`.
2. После получения блокировки заново прочитать актуальное состояние объекта.
3. Проверить существование, активность, удаление и вместимость.
4. Проверить пересечение с неотменёнными бронированиями.
5. Если пересечение найдено — откатить транзакцию и вернуть `Error.Conflict`.
6. Иначе вставить бронирование и зафиксировать транзакцию.

Рекомендуемый уровень изоляции — `ReadCommitted`. Он достаточен при условии, что блокировка строки объекта приобретается до проверки пересечений и все конкурирующие операции используют тот же объект как lock key.

### Почему двойная запись будет исключена

Пусть запросы A и B одновременно бронируют один объект:

1. A начинает транзакцию и блокирует строку объекта.
2. B пытается заблокировать ту же строку и ждёт.
3. A проверяет интервал, вставляет запись и выполняет commit.
4. B получает блокировку после commit A.
5. Запрос проверки B выполняется уже после получения блокировки и видит запись A.
6. B возвращает `409 Conflict`, ничего не вставляя.

Блокировка действует только на конкретный объект. Бронирования разных объектов выполняются параллельно.

### Обязательное условие корректности

Этот протокол должны использовать:

- создание бронирования;
- изменение дат или объекта бронирования, если такая операция появится;
- переход из неблокирующего статуса в блокирующий;
- повторное подтверждение отменённого бронирования, если оно будет разрешено.

Нельзя сначала проверить доступность, затем отдельно открыть транзакцию и выполнить вставку: это вновь создаст окно гонки.

### Перспективное усиление

После стабилизации модели статусов можно дополнительно ввести exclusion constraint. Наиболее прозрачный вариант — явный согласованный признак блокировки в строке `bookings`, изменение которого происходит вместе со статусом. Тогда PostgreSQL станет последней линией защиты даже для прямых SQL-операций.

## 3. Подробный алгоритм выполнения запроса

### 3.1. Условие пересечения

Для существующего интервала `[existingStart, existingEnd)` и нового `[newStart, newEnd)`:

```sql
existing.start_date_time < @newEnd
AND existing.end_date_time > @newStart
```

Полный запрос:

```sql
SELECT EXISTS
(
    SELECT 1
    FROM bookings AS b
    WHERE b.booking_object_id = @bookingObjectId
      AND b.status_id <> @cancelledStatusId
      AND b.start_date_time < @newEnd
      AND b.end_date_time > @newStart
);
```

Поведение:

| Существующий | Новый | Результат |
|---|---|---|
| `[10:00, 12:00)` | `[10:00, 12:00)` | Пересечение |
| `[10:00, 12:00)` | `[11:00, 13:00)` | Пересечение |
| `[10:00, 12:00)` | `[09:00, 11:00)` | Пересечение |
| `[10:00, 14:00)` | `[11:00, 12:00)` | Пересечение |
| `[11:00, 12:00)` | `[10:00, 14:00)` | Пересечение |
| `[10:00, 12:00)` | `[12:00, 14:00)` | Нет пересечения |
| `[10:00, 12:00)` | `[08:00, 10:00)` | Нет пересечения |

Строгие операторы `<` и `>` обеспечивают полуоткрытую семантику и разрешают соприкасающиеся интервалы.

### 3.2. Обработка запроса

1. Endpoint требует аутентификацию через `.RequireAuthorization()`.
2. `UserId` извлекается из `ClaimsPrincipal`:

   - сначала claim `sub`;
   - при необходимости совместимости — `ClaimTypes.NameIdentifier`;
   - значение должно разбираться как непустой `Guid`;
   - отсутствие или некорректность claim возвращает `401`.

3. Начальный статус определяется сервером, а не из `StatusId` запроса.
4. Проверяются локальные инварианты:

   - `StartDateTime < EndDateTime`;
   - `GuestsCount > 0`;
   - даты соответствуют принятому UTC-контракту.

5. Начинается транзакция.
6. Выполняется параметризованный запрос:

```sql
SELECT booking_object_id
FROM booking_objects
WHERE booking_object_id = @id
FOR UPDATE;
```

7. Если физической строки нет — `404`.
8. Объект читается с учётом `IsDeleted` и `IsActive`:

   - удалённый — `404` либо `409`, решение требуется согласовать;
   - неактивный — рекомендован `409`;
   - `GuestsCount > Capacity` — `400`.

9. Проверяется наличие пересечения с любым статусом, кроме `Отменено`.
10. При пересечении транзакция откатывается, возвращается:

```text
Error.Conflict(
    "booking.interval.conflict",
    "Выбранный интервал уже занят")
```

Endpoint преобразует это в HTTP 409.

11. Создаётся `Booking` с:

   - пользователем из JWT;
   - серверным начальным статусом;
   - нормализованными UTC-датами.

12. Выполняются `SaveChangesAsync(cancellationToken)` и commit.
13. При отмене запроса, исключении или ошибке commit транзакция откатывается.
14. В журнал записываются идентификаторы бронирования и объекта, но не персональные данные или содержимое токена.

## 5. Изменения API и совместимость

### Рекомендуемый переходный вариант

На первом этапе сохранить поля `UserId` и `StatusId` в `CreateBookingRequest`, чтобы не сломать текущий Frontend, но полностью игнорировать их:

- владелец определяется только JWT;
- начальный статус определяется только сервером.

Это безопаснее, чем сравнивать значения и доверять совпадению. В OpenAPI поля следует пометить устаревшими, а Frontend — перевести на новый контракт.

На втором этапе удалить их из request DTO после обновления потребителей.

### Предпочтительный целевой контракт

```text
BookingObjectId
StartDateTime
EndDateTime
GuestsCount
Comment
```

`UserId` и `StatusId` отсутствуют.

### Ответы API

| Ситуация | HTTP |
|---|---:|
| Нет JWT или токен некорректен | 401 |
| Нет прав на административную операцию | 403 |
| Объект физически отсутствует | 404 |
| Некорректные даты/гости/формат времени | 400 |
| Превышена вместимость | 400 |
| Объект неактивен | 409 |
| Интервал занят | 409 |
| Недопустимый переход статуса | 409 |

### Временная совместимость

Целевой контракт должен принимать момент времени однозначно. Предпочтительно перейти к `DateTimeOffset` в API, нормализуя значение в UTC перед сохранением.

Поскольку это изменение публичного DTO, для первого этапа возможен совместимый режим:

- оставить `DateTime`;
- принимать только значения с однозначной UTC-семантикой;
- отклонять `Unspecified` и локальные значения;
- требовать ISO 8601 с суффиксом `Z`.

Нельзя молча считать текущие значения локальными или UTC: существующие данные сначала нужно исследовать.

## 6. Необходимые изменения схемы БД

### Обязательные

Добавить ограничения:

```sql
CHECK (start_date_time < end_date_time)
CHECK (guests_count > 0)
```

Существующий индекс по объекту и датам можно оставить для поиска, но следует проверить план выполнения overlap-запроса на реальном объёме данных.

Перед добавлением check constraints необходимо провести диагностический запрос на существующие некорректные строки. Автоматически исправлять или удалять их нельзя.

### Для выбранной конкурентной защиты

Новая таблица или колонка не требуется. Блокировка использует существующую строку `booking_objects`.

Нужно определить:

- timeout ожидания блокировки;
- обработку cancellation token;
- преобразование timeout/deadlock в безопасную серверную ошибку;
- порядок блокировки, если операция в будущем затрагивает несколько объектов.

### Дополнительное усиление

Если будет выбран exclusion constraint, потребуется:

1. Расширение `btree_gist`.
2. Явный локальный признак блокировки в `bookings`.
3. GiST exclusion constraint по объекту и временному диапазону.
4. Обработка PostgreSQL SQLSTATE нарушения exclusion constraint как HTTP 409.
5. Синхронное изменение статуса и признака блокировки.
6. Предварительная очистка уже существующих пересечений.

## 7. План тестирования

### Unit-тесты Domain

- `start < end` — успех.
- `start == end` — validation error.
- `start > end` — validation error.
- `GuestsCount == 0` — validation error.
- отрицательный `GuestsCount` — validation error.
- корректный переход статуса.
- запрещённый переход из `Отменено`.

### Тесты Application handler

- UserId извлекается из `sub`.
- Отсутствующий claim даёт authentication error.
- Клиентские `UserId` и `StatusId` не используются.
- Начальный статус назначается сервером.
- Превышение вместимости даёт validation error.
- Неактивный объект даёт conflict.
- удалённый/отсутствующий объект даёт согласованный результат.
- репозиторный конфликт преобразуется в `Error.Conflict`.

### PostgreSQL integration-тесты

InMemory provider для конкурентной проверки непригоден. Тесты должны выполняться на реальном PostgreSQL, например в изолированном контейнере.

1. Свободный интервал успешно создаётся.
2. Полностью совпадающий интервал возвращает 409.
3. Частичное пересечение слева возвращает 409.
4. Частичное пересечение справа возвращает 409.
5. Вложенный интервал возвращает 409.
6. Интервал, содержащий существующий, возвращает 409.
7. `[10:00, 12:00)` и `[12:00, 14:00)` оба создаются.
8. Отменённая запись не блокирует новый интервал.
9. Неотменённый статус блокирует интервал.
10. DB check constraints отвергают некорректные данные даже при обходе Domain.

### Конкурентный тест

- Создать один объект.
- Открыть два независимых scope/`DbContext`.
- Синхронно запустить два запроса на один интервал.
- Убедиться, что запросы действительно перекрылись по времени.
- Ожидать:

  - ровно один успешный результат;
  - ровно один `409 Conflict`;
  - в БД ровно одна блокирующая запись.

Дополнительно повторить тест для разных объектов: оба запроса должны пройти без взаимной блокировки.

### Статусы

- Отмена освобождает интервал.
- Повторное подтверждение отменённой записи запрещено с 409.
- Если восстановление разрешено бизнесом — оно проходит через блокировку и получает 409 при уже занятом интервале.

### Авторизация

- `POST /api/bookings` без токена — 401.
- С валидным токеном — используется пользователь из токена.
- Подмена `UserId` в старом request не меняет владельца.
- Обычный пользователь не может подтверждать чужие бронирования, если подтверждение является административной операцией.

## 8. Критерии готовности

### Обязательные для устранения двойных бронирований

- Проверка пересечения использует полуоткрытую семантику `[start, end)`.
- Проверка и вставка находятся в одной транзакции.
- Перед проверкой берётся блокировка строки объекта.
- Все пути перехода из неблокирующего статуса в блокирующий используют тот же lock protocol.
- Конфликт возвращает `ErrorType.CONFLICT` и HTTP 409.
- Два параллельных запроса создают только одну запись.
- Даты и положительное число гостей защищены в Domain и check constraints.
- Проверяются существование, активность, удаление и вместимость объекта.
- Интеграционные тесты выполняются на PostgreSQL.

### Дополнительные улучшения безопасности

- Endpoint требует JWT.
- Владелец берётся из claim, клиентский `UserId` игнорируется.
- Статус назначается сервером, клиентский `StatusId` игнорируется.
- Confirm/Cancel проверяют владельца или административную роль.
- Вводится явная машина переходов статусов.
- Имена статусов заменяются стабильными кодами.
- Добавляется централизованная безопасная обработка ошибок БД.
- После стабилизации модели рассматривается exclusion constraint.
