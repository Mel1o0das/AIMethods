# Правила для AI-агента Codex — BookingService

> Назначение: сопровождение существующего сервиса бронирования бань и глэмпингов.  
> Агент: Codex (VS Code / CLI).  
> Основной источник сведений о проекте — текущие исходные файлы, а не предположения.

## Role — роль агента

**R01.** Действуй как C#/.NET-разработчик, который сопровождает уже существующий сервис бронирования. Перед правками изучай относящиеся к задаче файлы и их вызовы. Не предлагай полную переработку проекта, если её явно не запросили.

**R02.** Сначала кратко сформулируй цель, затрагиваемые части проекта и риски; для неоднозначных бизнес-правил задай уточняющий вопрос либо явно перечисли необходимые предположения. Для узких, очевидных изменений переходи к реализации без лишнего планирования.

## Context — контекст проекта

**R03.** Backend — ASP.NET Core на .NET 10. Сохраняй существующие четыре проекта и их ответственность: `BookingService.Domain` (сущности, Value Objects, ошибки), `BookingService.Application` (сценарии, контракты, endpoints), `BookingService.Infrastructure.Postgres` (EF Core и PostgreSQL), `BookingService.Core` (композиция приложения, middleware и запуск).

**R04.** Новые API-операции добавляй по действующему образцу `BookingService.Application/Features/<Feature>/` с `IEndpoint` и обработчиком. Не вводи параллельный набор MVC-контроллеров, если задача не предполагает изменения архитектуры.

**R05.** Следуй действующим зависимостям: `Domain` не ссылается на `Application`, инфраструктуру, HTTP и UI; `Application` зависит от доменных типов и абстракций; реализации доступа к данным размещаются в `Infrastructure.Postgres`; связывание выполняется в `Core`.

**R06.** В текущей реализации есть сущности `Booking`, `BookingObject`, `User`, `BookingStatus`, `Role` и типизированные идентификаторы (`BookingId`, `BookingObjectId`, `UserId` и др.). До создания новой сущности, DTO или сервиса проверь, нет ли аналогичной модели и контрактов.

**R07.** Frontend организован на Next.js/React/TypeScript: страницы находятся в `src/app`, повторно используемые компоненты — в `src/app/components`, запросы к API — в `src/app/services`, модели — в `src/app/models`. Используется Ant Design. Точные версии зависимостей проверяй по `package.json`, когда этот файл будет доступен; не выдумывай их.

## Style — стиль и технические соглашения

**R08.** Соблюдай `.editorconfig` и `Directory.Build.props`. В C# применяй принятые именования типов, методов и свойств в `PascalCase`, параметров и локальных переменных — в `camelCase`, приватных полей — с `_`. Не проводи массовое переформатирование несвязанных файлов.

**R09.** Используй включённые nullable reference types и типы, отражающие возможность отсутствия значения. Не подавляй предупреждения анализаторов и не используй `null!`, `#pragma` или `!` для скрытия новой ошибки без обоснования.

**R10.** Для проверки строковых и других ограниченных значений предпочитай существующие Value Objects и их методы `Create(...)`. Проверяй `IsFailure` перед обращением к `Value`, передавай ошибки через принятые типы `Error` и `Result<T, Error>`.

**R11.** Сохраняй принятый формат ответов `EndpointResult`, `CustomEnvelope` и HTTP-коды по типу ошибки: валидация — 400, отсутствие — 404, конфликт — 409, аутентификация — 401, отсутствие прав — 403. Не подменяй бизнес-ошибки безусловным `500` или успешным `200`.

**R12.** Для асинхронных вызовов БД используй `async`/`await` и по возможности передавай `CancellationToken` до EF Core. Для чтения без изменения сущностей применяй `AsNoTracking()` там, где это соответствует текущим паттернам.

**R13.** Изменения таблиц, EF Core-конфигураций и миграций выполняй согласованно. Версии NuGet задаются через `Directory.Packages.props`, а не независимо в каждом `.csproj`. Новую зависимость добавляй только при подтверждённой необходимости.

**R14.** Для React-компонентов используй TypeScript и существующие Ant Design-компоненты. Сохраняй HTTP-логику в сервисном слое; не копируй вызовы `fetch` между страницами и не меняй контракт Backend без проверки клиентских потребителей.

## Constraints — обязательные ограничения

**R15. СТРОГИЙ ЗАПРЕТ.** Не убирай, не обходи и не заменяй проверку JWT, ролей и принадлежности записи скрытием кнопок на Frontend. Любая новая операция чтения или изменения личных бронирований и административных данных должна проверять права на сервере. При обнаружении существующего незащищённого маршрута сообщи о риске; меняй соседние маршруты только по согласованному объёму задачи.

**R16. СТРОГИЙ ЗАПРЕТ.** Не допускай создание конфликтующих бронирований, полагаясь только на занятость, рассчитанную в интерфейсе, или на отдельную предварительную выборку без защиты от гонок. Перед реализацией согласуй правила пересечений, блокирующие статусы, часовой пояс и допустимость соприкасающихся интервалов; для параллельных запросов предложи транзакционную/БД-гарантию.

**R17. СТРОГИЙ ЗАПРЕТ.** Не включай реальные пароли, JWT signing keys, строки подключения, access tokens, персональные данные и содержимое `.env` в промпты, код, коммиты, тестовые фикстуры или отчёты. Если в проекте найдены действующие секреты, укажи на необходимость их ротации и переноса в безопасное хранилище, не повторяя значения.

**R18.** Не доверяй переданным клиентом `UserId`, `RoleId` и `StatusId` там, где значение должно определяться авторизованным пользователем или серверным процессом. При изменении затронутой операции проверь возможность повышения привилегий и подмены владельца.

**R19.** Не изменяй публичные DTO, маршруты, статусы, миграции, структуру решения и сигнатуры методов без оценки обратной совместимости. Если такое изменение действительно необходимо, покажи, какие вызовы Frontend и данные БД оно затронет.

**R20.** Не изменяй посторонние файлы, не удаляй пользовательские данные и не выполняй разрушительные операции (`drop database`, очистку таблиц, принудительный reset Git, публикацию секретов) без явного разрешения.

**R21.** Для создания и редактирования бронирования проверяй `StartDateTime < EndDateTime`, корректность временной зоны, положительное `GuestsCount` и ограничения вместимости. Не считай наличие соответствующей проверки на Frontend доказательством её наличия в домене или API.

**R22.** Перед окончательным выводом проверь не только «счастливый путь», но и отрицательные сценарии: неверные поля, отсутствующая запись, чужое бронирование, недопустимый статус и конкурирующие запросы, если они относятся к задаче.

## Format — формат изменений и ответа

**R23.** Предлагай минимальный набор файлов и сохраняй принятую организацию `Features`, Domain/Infrastructure и `src/app`. Для новой операции кратко перечисли назначение каждого нового или изменённого файла; не создавай абстракции на будущее без нужды.

**R24.** Перед завершением выполни доступные проверки. Для Backend сначала используй `dotnet build BookingService.sln` из каталога решения, затем подходящие тесты (`dotnet test`, если тестовые проекты присутствуют). Для Frontend запускай команды только после проверки реальных скриптов в `package.json`.

**R25.** В итоговом ответе укажи: что изменено; какие файлы затронуты; какие решения приняты; какие команды реально выполнены и чем закончились; какие риски и ограничения остались. Если сборка или тесты не запускались либо завершились ошибкой, сообщи об этом прямо, не объявляя их успешными.
