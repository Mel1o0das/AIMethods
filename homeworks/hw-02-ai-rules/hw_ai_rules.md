# Домашнее задание № 2. Анализ проекта и требований к AI-агенту

## 1. Описание проекта

В качестве основы домашнего задания используется существующий учебный проект **BookingService** — веб-сервис бронирования бань и объектов загородного отдыха (глэмпингов). Проект развивает ранее выполненную курсовую работу по дисциплине «Технологии веб-программирования». Основные пользователи системы — клиенты, оформляющие бронирования, и администраторы, управляющие объектами и заявками.

Система включает каталог объектов, регистрацию и авторизацию, выбор дат и времени, оформление и отмену бронирования, просмотр собственных заявок, а также административные функции. Для работы с занятостью предусмотрены маршруты получения забронированных интервалов. Клиентская и серверная части существуют отдельно и обмениваются данными по HTTP в формате JSON.

**Цель настройки AI-агента:** получать изменения, согласованные с архитектурой существующего проекта, избегать дублирования логики, сохранять совместимость API и не нарушать безопасность бронирований и пользовательских данных.

## 2. Используемые технологии

## 3. Существующая архитектура

Backend расположен в `backend/BookingService` и состоит из четырёх проектов:

1. `BookingService.Domain` — сущности `Booking`, `BookingObject`, `User`, статусы и роли, строго типизированные идентификаторы и Value Objects с проверкой значений.
2. `BookingService.Application` — интерфейсы репозиториев, обработчики бизнес-операций в `Features`, маппинг API-маршрутов и преобразование результатов в HTTP-ответы.
3. `BookingService.Infrastructure.Postgres` — `BookingServiceDbContext`, EF Core конфигурации, миграции, реализации репозиториев, JWT-сервис и хеширование паролей.
4. `BookingService.Core` — запуск приложения, регистрация зависимостей, CORS, Swagger, аутентификация, middleware и логирование.

Frontend в предоставленном архиве находится в `src/app`: страницы в файловых маршрутах Next.js, переиспользуемые компоненты в `components`, работа с HTTP в `services`, модели в `models`, стили в `styles`, пользовательская сессия в `context`.

## 4. Действующие соглашения о разработке

- Не нарушать направление зависимостей между слоями: доменная модель не должна зависеть от HTTP или инфраструктуры.
- Новую Backend-функциональность размещать в соответствующем каталоге `BookingService.Application/Features`, следуя принятому паттерну обработчиков.
- Доступ к PostgreSQL реализовывать через существующие интерфейсы и репозитории, используя EF Core и конфигурации сущностей.
- Не создавать DTO и сущности с дублирующими обязанностями, когда в проекте уже имеются подходящие модели.
- Для бизнес-операций сохранять принятую обработку `Result<T, Error>` и существующее соглашение об HTTP-кодах.
- Для идентификаторов и проверяемых строк использовать существующие Value Objects и фабричные методы, если это применимо.
- Использовать `async`/`await`, учитывать `CancellationToken` при операциях, которые могут быть отменены.
- Соблюдать настройки `Directory.Build.props`, `.editorconfig`, StyleCop и централизованное управление пакетами через `Directory.Packages.props`.
- На Frontend сохранять разделение React-компонентов и сервисов HTTP-запросов, использовать TypeScript и Ant Design.
- Не добавлять новые пакеты, не менять API-контракты и миграции БД без проверки последствий для остальных модулей.
- Не включать пароли, JWT-ключи и строки подключения с действующими реквизитами в код, отчёты, промпты и репозиторий.

Эти положения служат исходными требованиями для разработки формального файла правил AI-агента на следующем шаге ДЗ №2.

## 5. Ключевые функции и ограничения предметной области

В проекте присутствуют две разновидности бронирований: глэмпинги с выбором дат и бани с выбором времени сеанса. Для создания бронирования важны интервал начала и конца, количество гостей, объект, пользователь и статус заявки. На Frontend уже используется запрос занятых интервалов и ограничение выбора дат/времени.

В правилах для AI необходимо закрепить, что проверка доступности в интерфейсе не заменяет серверную проверку. Сервер должен самостоятельно валидировать интервал и учитывать пересечения, в том числе при конкурентных запросах. Проверка авторизации и прав также должна выполняться на стороне API, а не только скрытием элементов интерфейса.

## 6. Наблюдения по исходникам, требующие отдельной проверки

При статическом просмотре предоставленного кода выявлены вопросы, важные для безопасной дальнейшей разработки:

1. В `Features/Bookings/Create.cs` и `BookingRepository.AddAsync` нет видимой проверки пересечения бронирований перед сохранением. Маршруты чтения занятости существуют, а интерфейс использует полученные интервалы. Это не равно доказанной серверной защите от конфликтов.
2. Явное `.RequireAuthorization()` обнаружено у `/auth/me`; у маршрутов изменения бронирований и управления объектами в изученных файлах оно отсутствует. Необходимо отдельно проверить настройки политик и исправить защиту чувствительных операций.
3. Запрос регистрации принимает `RoleId` от клиента. До использования в реальном сервисе необходимо исключить возможность самостоятельного назначения привилегированной роли.
4. Исходный `appsettings.json` содержит заполненные поля с потенциально конфиденциальной конфигурацией. Действующие секреты должны храниться вне репозитория и при необходимости быть заменены.
5. В представленном решении не найден отдельный проект автоматических тестов. Практическая часть ДЗ №2 может стать отправной точкой для создания воспроизводимых тестов.
6. Архив клиентского кода содержит `src`, но не содержит корневые файлы конфигурации Next.js. Их можно добавить позже перед настройкой сборки и тестирования Frontend.

Эти пункты являются результатом статического анализа предоставленных файлов, **не** результатом запуска приложения или эксплуатации уязвимостей.

## 7. План работы с Codex

Файл инструкций для Codex предлагается разместить в `AGENTS.md` в корне рабочей копии проекта; копию правил предоставить преподавателю как `rules.md`. Содержание должно включать роль агента, контекст проекта, стиль, ограничения и формат выдаваемых изменений. По требованиям ДЗ №2 необходимо не менее десяти правил, включая минимум два строгих запрета.

Для библиотеки промптов будут подготовлены пять шаблонов RTCF: генерация функциональности, рефакторинг, тесты, исправление ошибок, декомпозиция. Каждый получит пример, связанный с BookingService.

В качестве сложной задачи для последовательной работы с AI предлагается **усиление серверной проверки бронирований**: анализ текущего поведения, проектирование атомарной защиты от конфликтов, реализация с тестами. Для корректного сравнения «без правил / с правилами» следует использовать две независимые копии одной исходной версии проекта и сохранять реальные ответы агента, код и результаты сборки.

## 8. Границы проведённого анализа
