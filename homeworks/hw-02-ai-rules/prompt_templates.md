# Домашнее задание № 2. Библиотека промпт-шаблонов

**Проект:** BookingService — веб-сервис бронирования бань и глэмпингов.  
**AI-агент:** Codex.  
**Метод составления промптов:** RTCF (Role, Task, Context, Format).

## Назначение

Шаблоны предназначены для сопровождения существующей системы, а не для генерации нового проекта с нуля. В серверной части используются C# и ASP.NET Core (.NET 10), четыре проекта (`Domain`, `Application`, `Infrastructure.Postgres`, `Core`), EF Core, PostgreSQL, `IEndpoint`, `Result<T, Error>` и Value Objects. Клиентская часть построена на React/Next.js и TypeScript.

Каждый шаблон состоит из четырёх обязательных частей:

- **Role (роль)** — в качестве какого специалиста действует агент.
- **Task (задача)** — какое конкретно изменение или исследование требуется.
- **Context (контекст)** — какие файлы, ограничения, бизнес-правила и исходные сведения нужно учитывать.
- **Format (формат)** — в каком виде предоставить изменения и результаты проверок.

Для повторного использования заполняются поля в угловых скобках. Примеры ниже являются готовыми запросами для конкретных задач BookingService, но **не являются отчётами о выполнении**. Фактические ответы и результаты Codex должны быть сохранены отдельно после запуска.

> **Условия работы:** выполнять задачи в отдельной копии проекта; не выводить реальные секреты и персональные данные; перед изменениями проверять существующие реализации. Наличие `AGENTS.md` нужно учитывать при практическом использовании шаблонов. Для отдельного эксперимента «до правил / после правил» используются независимые копии с одинаковым исходным состоянием.

## Шаблон 1. Генерация компонента или функции по описанию

### Шаблон RTCF

**Role:** Ты — разработчик C#/.NET, сопровождающий существующий Backend BookingService. Соблюдай принятые архитектурные границы и стиль проекта.

**Task:** Реализуй `<название новой функции>` с поведением `<проверяемое поведение>`. Измени только файлы, необходимые для задачи; не переписывай соседние функции без необходимости.

**Context:** Перед реализацией прочитай `<существующие файлы и вызовы>`. Используй текущую архитектуру (`Domain`, `Application`, `Infrastructure.Postgres`, `Core`), принятые Value Objects, `Result<T, Error>` и существующие интерфейсы. Условия и пограничные случаи: `<условия>`. Изменения публичного API: `<разрешены или запрещены>`. Секреты и продуктивные данные не используй.

**Format:** Сначала кратко перечисли затрагиваемые файлы и допущения. Затем реализуй код. В конце укажи изменения по файлам, результаты реально выполненных команд сборки и тестов, а также непроверенные случаи. Не заявляй об успешном тестировании, если оно не проводилось.

### Пример использования

**Role:** Ты — C#/.NET-разработчик, работающий с доменными моделями BookingService.

**Task:** Добавь функцию проверки корректности временного интервала бронирования: начало должно строго предшествовать окончанию. При ошибке нужно получать доменную ошибку в существующем формате, а не исключение общего типа.

**Context:** Изучи `BookingService.Domain/Bookings/Booking.cs`, `BookingService.Domain/Shared/Error.cs` и примеры создания Value Objects в `BookingService.Domain/ValueObjects/`. Уже существующая фабрика `Booking.Create(...)` возвращает `Result<Booking, Error>`. Не меняй сигнатуры внешних API, формат сохранения в PostgreSQL и значения статусов. Границы интервала — `[начало, конец)`; вопрос часового пояса зафиксируй как отдельно требующий согласования, если он влияет на реализацию.

**Format:** Покажи перечень затронутых файлов, точное изменение доменной логики, примеры корректного и некорректного ввода и результаты сборки/тестов. Не изменяй посторонние компоненты.

**Что проверяется в результате:** бизнес-валидация находится на Backend; ошибочный интервал не приводит к созданию объекта; действующие вызовы фабрики остаются совместимыми.

## Шаблон 2. Рефакторинг существующего кода

### Шаблон RTCF

**Role:** Ты — C#/.NET-разработчик, выполняющий рефакторинг существующего кода с сохранением поведения.

**Task:** Улучши реализацию `<метод/класс>` в части `<читаемость/устранение дублирования/обработка ошибок>`. Сохрани внешнее поведение и публичные контракты, если их изменение отдельно не согласовано.

**Context:** Проанализируй `<конкретные исходные файлы>`, вызывающие места и зависимые типы. Сохраняй архитектуру BookingService, `Result<T, Error>`, принятые коды HTTP и совместимость с потребителями Frontend. Известные риски: `<перечень>`. Не делай посторонних изменений.

**Format:** Представь краткий список проблем исходного кода, перечень точечных изменений, список затронутых файлов, результаты тестов и оставшиеся риски. Приведи сравнение поведения до и после на нескольких сценариях.

### Пример использования

**Role:** Ты — разработчик ASP.NET Core с опытом поддержки Clean Architecture.

**Task:** Проведи минимальный рефакторинг `CreateBookingHandler.Handle(...)`: исключи небезопасное обращение к `booking.Value` до проверки `booking.IsFailure`, сохрани существующие бизнес-контракты и добавь явное распространение доменной ошибки. Новую функциональность бронирований пока не вводи.

**Context:** Изучи `BookingService.Application/Features/Bookings/Create.cs`, `BookingService.Domain/Bookings/Booking.cs`, `IBookingRepository.cs` и примеры обработки `Result<T, Error>` в других `Features`. Не меняй поля `CreateBookingRequest`, маршрут `/bookings`, формат ответа `EndpointResult` и схему БД. Учитывай, что фабрика `Booking.Create(...)` возвращает `Result<Booking, Error>`.

**Format:** Укажи исходный риск, изменённые участки и сценарии: создание валидного бронирования, ошибка доменной фабрики, ошибка сохранения в репозитории. Запусти доступные проверки; если автоматических тестов нет, не называй ручную проверку автоматической.

**Что проверяется в результате:** обоснованность рефакторинга, небольшой дифф, корректное распространение ошибок, отсутствие незапрошенных изменений.

## Шаблон 3. Написание тестов для существующего кода

### Шаблон RTCF

**Role:** Ты — разработчик автоматизированных тестов C#/.NET, знакомый с xUnit, тестированием доменной логики и API.

**Task:** Добавь тесты для `<класс/метод/сценарий>`, включая успешный сценарий и перечисленные ошибки: `<ошибки>`. Не меняй рабочий код для искусственного прохождения тестов без отдельного согласования.

**Context:** Изучи `<исходные файлы>`, сигнатуры методов, типы результатов и текущие тестовые проекты. Если тестового проекта нет, сначала предложи минимальный вариант подключения и укажи нужные пакеты. Не подключай реальную БД без необходимости и не используй действующие учётные данные.

**Format:** Предоставь список тест-кейсов с ожидаемыми результатами, новые или изменённые тестовые файлы и фактический вывод `dotnet test`. Если тест выявил дефект, выдели его отдельно; не скрывай падение изменением ожидаемого результата.

### Пример использования

**Role:** Ты — C# QA Automation Engineer, работающий с xUnit и ASP.NET Core.

**Task:** Создай автоматические тесты для `Booking.Create(...)` и `CreateBookingHandler.Handle(...)`. Проверь позитивное создание бронирования, передачу ошибки из доменной фабрики и обработку ошибки сохранения репозитория. Если часть сценариев сегодня не поддерживается, зафиксируй падающий тест как обнаруженный дефект.

**Context:** Изучи `BookingService.Domain/Bookings/Booking.cs`, `BookingService.Application/Features/Bookings/Create.cs`, `IBookingRepository.cs`, `BookingService.Domain/Shared/Error.cs`. В текущем переданном Backend отдельного тестового проекта не обнаружено. Сначала выясни это в полной локальной копии и только затем создай минимальный xUnit-проект, если его действительно нет. Для ошибок репозитория используй тестовый double; не обращайся к рабочей PostgreSQL и не используй продуктивные данные.

**Format:** Составь таблицу «сценарий — входные данные — ожидаемый результат», добавь тесты и выведи число запущенных, успешных и проваленных проверок. Отдельно перечисли ошибки текущей реализации, если они выявились.

**Что проверяется в результате:** тесты воспроизводимы, действительно проверяют поведение и не требуют производственной БД.

## Шаблон 4. Исправление ошибки или бага

### Шаблон RTCF

**Role:** Ты — инженер по диагностике ошибок ASP.NET Core / EF Core с акцентом на сохранение совместимости и безопасность данных.

**Task:** Найди причину `<симптом/ошибка/неверный HTTP-код>` и исправь её минимальным изменением. Сначала воспроизведи проблему или сформулируй проверяемую гипотезу.

**Context:** Используй `<логи, воспроизводящие действия, маршруты, файлы>`. Не предполагай, что ошибка находится именно в указанном месте; проследи путь вызовов. Учитывай текущую систему авторизации, формат `Result<T, Error>` и ограничения PostgreSQL. Если нужны реальные ключи или пароли, не запрашивай их для вывода в чат.

**Format:** Верни последовательность «симптом → подтверждённая причина → исправление → регрессионная проверка», перечень изменённых файлов, результаты команд и возможные побочные эффекты. Если причина не подтверждена, явно обозначь это.

### Пример использования

**Role:** Ты — разработчик Backend с опытом поиска ошибок в REST API и доменных моделях.

**Task:** Исследуй ситуацию, когда `POST /bookings` принимает запрос с `StartDateTime >= EndDateTime` и может попытаться создать запись. Требуется определить, воспроизводится ли это на текущем коде, и обеспечить корректную доменную ошибку вместо принятия некорректного интервала. Не меняй другие правила бронирования без необходимости.

**Context:** Проверь `BookingService.Application/Features/Bookings/Create.cs`, `BookingService.Domain/Bookings/Booking.cs`, `IBookingRepository` и соответствующую инфраструктурную реализацию. В представленном исходнике фабрика `Booking.Create(...)` не содержит явной проверки порядка дат. Зафиксируй ожидаемый HTTP-код `400` через действующую схему `Error` / `EndpointResult`; проверь граничный случай одинаковых дат. Не подменяй проблему проверкой только на Frontend.

**Format:** Покажи способ воспроизведения, точечное изменение, тест на ошибочный интервал и вывод реально проведённых проверок. Укажи, если запуск был невозможен из-за окружения.

**Что проверяется в результате:** подтверждение причины по коду или воспроизведению, корректный ответ и отсутствие регрессий.

**Context:** Учитывай четырёхслойную архитектуру, EF Core и PostgreSQL, текущую обработку ошибок, статусы бронирований и клиентские вызовы API. Сначала проверь существующую реализацию `<соответствующие файлы>`. Неоднозначные правила `<перечень>` сначала вынеси в вопросы, а не выбирай произвольно.

**Format:** Выдай план минимум из трёх этапов в порядке выполнения. По каждому этапу: цель, файлы/модули, тесты, критерии готовности, риски. Затем предложи отдельные промпты для последовательной работы с агентом. Реализацию в рамках этого запроса не выполняй.

### Пример использования

**Role:** Ты — архитектор ASP.NET Core/EF Core, отвечающий за целостность данных при параллельных запросах.

**Task:** Разбей на этапы реализацию гарантированного запрета пересекающихся бронирований одного объекта, в том числе при одновременной отправке двух запросов. Сейчас нужен только план, без изменения файлов.

**Context:** Изучи `BookingService.Application/Features/Bookings/Create.cs`, `BookingService.Application/Features/Bookings/IBookingRepository.cs`, реализации репозитория в `BookingService.Infrastructure.Postgres`, текущие запросы доступности и конфигурацию таблицы `Bookings`. Отдельно рассмотри гарантию на уровне транзакции/БД, а не только предварительный `SELECT`.

**Format:** Подготовь не менее трёх этапов: (1) уточнение правил и тест-кейсов, (2) проектирование серверной/БД-защиты, (3) реализация и проверка конкуренции. Для каждого составь отдельный промпт и критерии приёмки. Не выполняй миграции без согласования.

**Что проверяется в результате:** последовательность действий, отсутствие опасных предположений и наличие плана тестирования конкурентных запросов.

## Применение шаблонов в работе

1. Выбрать один из пяти сценариев и подставить в его поля конкретную задачу, ссылки на исходники и ограничения.
2. Передать запрос Codex в контексте нужной копии BookingService. Для обычной разработки применяются правила `AGENTS.md`.
3. Сохранить исходный запрос, полный ответ агента, реально изменённые файлы и результаты запуска команд.
4. При необходимости сформулировать уточняющий промпт и отметить отдельную итерацию.
5. Для эксперимента ДЗ №2 с правилами и без правил выполнить **одну и ту же задачу** в двух независимых копиях с идентичной исходной версией. Не переносить изменения одной копии в другую до завершения сравнения.

Тестирование шаблонов и результаты работы агента оформляются отдельно в `prompt_methodology.md` и `testing.md` в следующих шагах задания.
