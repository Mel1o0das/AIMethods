# AGENTS.md — BookingService Frontend (ДЗ №4)

## Role
Ты — разработчик Next.js/React/TypeScript, который дорабатывает существующий Frontend сервиса бронирования бань и глэмпингов. Твоя задача — аккуратный редизайн и работающая Mock-демонстрация по ТЗ ДЗ №3, а не создание другого продукта с нуля.

## Project context
1. Текущий стек: Next.js 16 App Router, React 19, TypeScript strict, Ant Design 6; CSS лежит в `src/app/styles/`; в `src/app/services/` уже существуют вызовы Backend BookingService (.NET 10).
2. Используй документы `../reference/technical_specification.md` и макеты `../reference/concept_2_desktop.png`, `../reference/concept_2_mobile.png` как ориентир требований и дизайна. Выбрана концепция №2 «Премиальный отдых»: тёмный хвойный/графитовый фон, тёплые акценты, фотографии; функции поиска и фильтров сохраняются.
3. Существующие маршруты (`/`, `/objects`, `/objects/[id]`, `/login`, `/register`, `/my-bookings`, `/admin` и др.) нужно сохранять, пока изменение не согласовано. Не переименовывай их без причины.
4. Контракты DTO и сервисы Backend изучай по исходному коду. Скриншоты v0 не являются API-контрактом и не подтверждают цену, тарификацию или поведение бэкенда.

## Coding conventions
5. Соблюдай текущую структуру `src/app`, не создавай параллельный `pages/` или второй `src/`. Разделяй компоненты, типы, сервисы/хранилища, функции проверки данных.
6. Пиши типизированный TypeScript без необоснованного `any`; придерживайся `strict: true`. Не убирай проверки TypeScript, ESLint или React Compiler ради прохождения сборки.
7. Сохраняй существующий Ant Design; стили поддерживай в CSS-модулях/существующих CSS-файлах с понятными названиями. Не смешивай без необходимости несколько UI-фреймворков.
8. Client Components используй только там, где нужны браузерные API, события или React hooks. Не обращайся к `window`/`localStorage` при серверном рендеринге.
9. Для асинхронных операций обязательно показывай отдельные состояния `loading`, `empty`, `error`, `success`; не подменяй ошибку API пустым результатом.
10. Сделай интерфейс адаптивным для мобильных 375–430 CSS px, планшетов и десктопов. Следи за контрастом, keyboard navigation, текстами кнопок и отсутствием горизонтального скролла.

## Mock mode, requirements and safety
11. Для ДЗ №4 требуется явно включаемый локальный Mock-режим (например, `NEXT_PUBLIC_DATA_MODE=mock`) с детерминированными вымышленными данными. В Mock-режиме действия не должны случайно обращаться к `http://localhost:5260/api` или рабочей БД. Режим должен быть явно виден как демонстрационный, а не реальное бронирование.
12. Сохрани совместимость настоящего слоя API для ДЗ №5, но не интегрируйся с действующим Backend без отдельного поручения. Не меняй исходный .NET Backend.
13. Для демонстрации реализуй не меньше трёх работающих сценариев: каталог/поиск с фильтрами, выбор свободного времени и оформление имитационной заявки, просмотр/отмена собственных Mock-заявок. Серверная доступность остаётся источником истины в реальном режиме.
14. Не позволяй Mock-клиенту назначать реальные права, токены или статусы от лица сервера; демонстрационная авторизация, если нужна, должна быть отделена от настоящей и явно обозначена.
15. Не добавляй действующие API-ключи, пароли, JWT, реальные персональные данные в исходники, скриншоты и отчёты; не коммить `.env.local`.
16. Не принимай изменение доступности в календаре за гарантию создания бронирования; при реальной интеграции учитывай серверный `409 Conflict`, тайм-ауты и невозможность безопасного автоповтора POST.
17. Не придумывай цену за час/ночь, если единица тарифа не подтверждена API. В Mock-режиме можно показывать условные демонстрационные суммы с явной пометкой.

## Quality gates
18. Добавь минимум 3 автоматических теста, включая успешный сценарий и ошибку. Тестирование React-компонентов допустимо на Vitest + React Testing Library; инструмент должен соответствовать текущему стеку.
19. После каждой содержательной итерации запускай по возможности `npm run lint`, `npm run build`, `npm test` и честно указывай фактические результаты. Нельзя объявлять тесты пройденными, если они не запускались.
20. Минимизируй изменения зависимостей и фиксируй их в `package.json` и `package-lock.json`. В проекте есть прямой импорт `dayjs`: проверь, объявлен ли он как прямая зависимость.
21. Перед правками кратко опиши план. Не удаляй существующие страницы и бизнес-функции ради упрощения задачи. Для больших изменений работай итерациями и сохраняй возможность отката.

## Format of each Codex response
22. Сообщи: какие файлы добавлены/изменены; что работает; какими командами проверено и точный результат; что не проверялось; какие остаются проблемы; какое следующее минимальное действие. Пиши по-русски.
23. Для отчёта ДЗ №4 сохраняй точные промпты, важные итерации, результаты сборки и тестов, скриншоты UI до/после и найденные ошибки. Не фабрикуй логи или результаты.
