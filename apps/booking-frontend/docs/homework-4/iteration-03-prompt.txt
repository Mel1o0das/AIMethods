Контекст и роль
Ты — Frontend-разработчик BookingService, существующего Next.js 16 / React 19 / TypeScript strict / Ant Design 6 приложения. Следуй AGENTS.md, ../reference/technical_specification.md, выбранной концепции №2 и текущей архитектуре приложения. Не создавай отдельное приложение и не переписывай Backend.
Уже существуют разделённые api/mock источники данных (data-source.ts, data-mode.ts, api-data-source.ts, mock-data-source.ts), UI-каталог после итерации 02, Vitest + React Testing Library, и 9 проходящих тестов по отчёту предыдущей итерации. Это результат предыдущей итерации, а не автоматически подтверждённый результат текущей. Прежде чем менять файлы, изучи их реальные последние версии и составь краткий план.
Цель и критерии готовности
Довести до работающего UI второй и третий сквозные Mock-сценарии ДЗ №4:
1. Каталог → карточка /objects/[id] → проверка занятости → выбор начала/конца и гостей → создание демонстрационного бронирования → явный успех.
2. /my-bookings → просмотр только своих демонстрационных бронирований → отмена через подтверждение → обновлённый статус и освобождение интервала.
Первый сценарий (каталог, поиск, фильтры) уже реализован: сохранить его без регрессий. Все три сценария должны работать в NEXT_PUBLIC_DATA_MODE=mock без единого реального HTTP-запроса. В api-режиме сохранить текущие рабочие вызовы и семантику авторизации; фронтенд не должен заявлять о проверенной реальной интеграции.

Шаг B — изолированная демонстрационная авторизация
1. Добавь прозрачный способ работать как один фиксированный демонстрационный пользователь в Mock-режиме (например, помеченный «Демо-пользователь» профиль). Данные исключительно вымышленные. Допустим вход по кнопке «Продолжить в демо-режиме» либо автоматическое включение демонстрационного профиля, если это проще для данной архитектуры. Пользователь должен понимать, что это не настоящий вход.
2. В Mock-режиме не вызывай /auth/login, /auth/me, /roles, /users или другие реальные URL. Ни один UI-обработчик не должен случайно переключаться в API. Не сохраняй настоящее JWT-подобное значение для демо; если нужен маркер сессии — используй отдельное пространство имён и не смешивай с localStorage['token']. Не создавай ложные права администратора (isAdmin = false). Не позволяй демо-режиму попасть на действующие административные действия.
3. При NEXT_PUBLIC_DATA_MODE=api сохрани прежнюю реальную авторизацию, хранение и обработку настоящих данных без искусственных демо-обходов. Не переписывай серверные permission checks — в этой итерации они не тестируются.
4. Обеспечь согласованность user.id, хранилища Mock-заявок и /my-bookings: демо-заявки видит и отменяет только связанный с ними демо-пользователь. Не отдавай глобальный список как «мои» без проверки userId.
5. Сохрани или восстанови заметную пометку «Демонстрационный режим · реальные заявки не создаются». На присланном скриншоте главной баннер не заметен — проверь, что он действительно виден при mock.
Шаг C — выбор интервала и создание заявки
6. Сохрани маршрут /objects/[id]; переоформи его в стилистике концепции №2 без потери данных объекта и CTA. Убери/замени недостоверные единицы тарифа. price в контракте не доказывает цену за час или ночь; для Mock-данных можно писать «Условная цена», «Демонстрационная сумма», а расчёт — только если явно определён как вымышленное допущение. Не показывай неподтверждённый обязательный платёж.
7. Реализуй в форме/компоненте корректные состояния loading / error + Повторить / empty для занятости и submitting / success / conflict для создания заявки. Если занятость не загрузилась, не делай вид, что время свободно. При ошибке загрузки статусов либо устранить необходимость статуса в Mock-UI, либо показывать честную ошибку без подавления через пустой catch.
8. Валидация: выбран существующий активный объект, начало раньше конца, начало в будущем, гостей от 1 до capacity, комментарий в допустимых пределах. Дополнительно соблюдай существующие подтверждённые правила продукта; не придумывай реальные тарифы и часовые пояса. Для Mock реализуй совместимые и явно задокументированные допущения о времени.
9. Проверка пересечений всего интервала, а не только начальной/конечной точек: для интервалов [start, end) пересечение есть, если startA < endB && endA > startB. Ровно примыкающие интервалы не конфликтуют. Начальную занятость и созданные демо-заявки учитывать вместе. При отмене освободить интервал, если это соответствует текущему Mock-договору. Инвариант проверять повторно в методе создания Mock-заявки, даже если календарь ранее показывал свободное место; показывать понятный конфликт и сохранять поля ввода.
10. Создание — одно действие на нажатие; пока запрос выполняется, submit disabled/loading. После успеха показать отдельный success с номером/идентификатором демо-заявки (если доступен) и действующей ссылкой/кнопкой «Мои бронирования». Не выдавать демонстрационную заявку за реальное подтверждение Backend. Не закрывать форму при ошибке без объяснения. Не делать автоматическую повторную отправку после тайм-аута с неизвестным исходом.
11. При обращении к API в api-режиме сохранить DTO и вызовы; в будущем сервер — источник истины для доступности, статуса и прав. Не менять CreateBookingPayload или статусы реального сервера лишь ради демонстрационной модели. Если обнаружено противоречие между старым UI и актуальным API, зафиксируй ограничение в отчёте.
Шаг D — мои заявки и отмена
12. Реализуй /my-bookings в общей тёмной стилистике: список заявок, название объекта, интервал, гости, статус, действие отмены. Сохрани поиск и фильтр статуса, если он работал раньше. У демо-пользователя показывай только его заявки; при пустом списке предложи перейти в каталог.
13. Раздели loading, empty (заявок нет), filtered-empty (нет по фильтрам), error (данные не получены) и success; при error должна работать кнопка «Повторить». Старое поведение .catch(() => message.error(...)) с бесконечным спиннером нужно устранить. Если список не загрузился — нельзя показывать «заявок нет».
14. Подтверждение отмены — явно через интерфейс. Во время запроса блокируй повторные клики. После успеха обнови список и статус из Mock-источника, а также занятость объекта; после сбоя оставь заявку без ложной отметки «Отменено» и покажи причину. Не допускай повторной отмены уже отменённой заявки. Обязательно проверить доступность формы и мобильную компоновку.
15. Демонстрационное хранилище может оставаться в памяти, как согласовано в итерации 01. Чётко сообщи пользователю, что при полной перезагрузке состояние может сброситься, и не объявляй это долговременным хранением. Переход между страницами без перезагрузки должен сохранять согласованность в рамках работающей сессии. Если текущая реализация имеет иной обоснованный механизм, сначала опиши его и тестируй фактическое поведение.

Шаг F — тесты и доказательства
20. Не удаляй 9 прежних тестов. Добавь UI/component + Mock-data тесты не только на статический рендер, а на поведение:
    - успешное бронирование свободного интервала от демо-пользователя, видимое в «Моих бронированиях»;
    - конфликт пересекающихся интервалов после первой заявки и отсутствие второй записи;
    - отмена заявки с изменением статуса и восстановлением доступности;
    - валидация неверного интервала/числа гостей, отсутствие создания;
    - ошибка загрузки занятости или заявок → error+retry, а не пустой список/вечный спиннер;
    - Mock-авторизация не обращается к реальной сети; fetch-шпион с исключением — 0 вызовов;
