## План итерации

1. Проверить актуальные Mock/API-адаптеры, форму бронирования, `/objects/[id]`, `/my-bookings` и авторизацию.
2. Отделить демонстрационного пользователя от JWT/API-авторизации.
3. Замкнуть Mock-поток: занятость → создание → просмотр своих заявок → отмена → освобождение интервала.
4. Разделить loading, empty, filtered-empty, error и success; добавить retry и защиту от повторных действий.
5. Добавить поведенческие тесты, выполнить lint, typecheck, test, две production-сборки и audit.

## Реализация

- В Mock-режиме `AuthProvider` предоставляет фиксированного пользователя `mock-user`, не читает реальный JWT, не загружает профиль/роли и не выдаёт административные права. `/login` объясняет демо-режим вместо показа настоящей формы входа.
- Верхняя панель и общий баннер явно обозначают демо-пользователя, отсутствие реальной заявки и сброс памяти после полной перезагрузки.
- `/objects/[id]` получил отдельные loading/error/success-состояния, повтор загрузки, условную цену и итог созданной заявки со ссылкой на `/my-bookings`.
- `BookingFormModal` загружает статусы и занятость через выбранный data source. Ошибка не превращается в пустую доступность: есть error + retry. На отправке блокируются повторные клики, а ошибка оставляет форму открытой.
- Проверяются будущая дата, `start < end`, целое число гостей `1..capacity`, комментарий до 500 символов, известный статус и пересечение по полуоткрытым интервалам `[start, end)`. Проверка повторяется внутри Mock-адаптера, поэтому прямой вызов сервиса не обходит правила.
- Для бань используется демонстрационный шаг времени 30 минут. Для глэмпинга явно подписано временное допущение: заезд 15:00, выезд 12:00. Это не объявлено контрактом Backend.
- Цена не пересчитывается по часам или ночам: исходное числовое поле показывается только как «условная сумма/цена».
- `/my-bookings` запрашивает записи текущего пользователя, различает загрузку, ошибку, настоящий пустой список, пустой результат фильтра и успешный список. Отмена требует подтверждения, блокирует повторный клик, передаёт владельца Mock-адаптеру, перечитывает список и освобождает интервал. Ошибка отмены не меняет статус локально.
- Mock-хранилище остаётся модульной памятью: переходы App Router сохраняют состояние, полная перезагрузка сбрасывает его к детерминированным данным.
- Реальный `apiDataSource` и Backend не менялись; добавленный необязательный `userId` при отмене используется для проверки владельца только в Mock-адаптере и не меняет HTTP-контракт API-ветки.

## Новые проверки

Тесты слоя данных (не называются UI-тестами):

- новая заявка видна владельцу и не видна другому пользователю;
- пересекающийся интервал отклоняется и вторая запись не появляется;
- отмена освобождает интервал, после чего тот же интервал можно занять снова;
- неверный порядок дат и превышение вместимости не изменяют хранилище;
- другой пользователь не может отменить чужую заявку;
- все Mock-операции выполняются при `fetch`-шпионе, который падает при вызове.

UI/component-тесты:

- Mock-авторизация показывает фиксированного не-администратора и делает 0 вызовов `fetch`, даже если в `localStorage` лежит старый токен;
- `/my-bookings` показывает ошибку загрузки, а «Повторить» действительно переводит страницу в корректный empty-state;
- пользователь открывает подтверждение отмены, подтверждает его и видит обновлённый статус «Отменено»; проверяется вызов с ID пользователя.

## Доказательство отсутствия HTTP в Mock-режиме

`rg -n 'localhost:5260|fetch\(' src/app` находит HTTP только в `auth.ts`, `users.ts`, `api-data-source.ts` и API-мутациях `booking.objects.ts`. Каталог, занятость и заявки читают `getBookingDataSource()`, который при `NEXT_PUBLIC_DATA_MODE=mock` возвращает `mockDataSource`. API-only операции имеют блокировку режима.

Автотесты устанавливают `NEXT_PUBLIC_DATA_MODE=mock`, заменяют глобальный `fetch` функцией, которая немедленно выбрасывает исключение, и ожидают 0 вызовов. Проверены каталог, статусы, занятость, создание, чтение, отмена, авторизация и блокировка несвязанных API-сервисов. Все 16 тестов прошли; следовательно, проверенные Mock-пути не отправили запрос на `http://localhost:5260/api` или другой URL.

## Как запустить и показать три сценария

PowerShell:

```powershell
$env:NEXT_PUBLIC_DATA_MODE="mock"
npm run dev
```

После изменения режима dev-сервер следует перезапустить.

1. Каталог: открыть `/`, выполнить поиск, перейти в `/objects`, применить тип/цену/вместимость/сортировку и открыть «Подробнее».
2. Бронирование: на `/objects/[id]` нажать создание демо-заявки, дождаться состояния занятости, выбрать будущий корректный интервал и допустимое число гостей. После success перейти по кнопке «Мои бронирования» и увидеть ID заявки.
3. Отмена: на `/my-bookings` найти свою заявку, нажать «Отменить заявку», подтвердить. Статус станет «Отменено», кнопка исчезнет, а интервал снова будет доступен в текущей сессии.

## Непроверенное и ограничения

- Реальный интерактивный браузер в сессии недоступен. Ручной сквозной прогон, геометрия на 375/390/430/768/1280 CSS px, клавиатурная навигация, открытый календарь/Drawer и горизонтальный скролл не подтверждены; скриншоты не создавались и не фабриковались.
- Даты/время бань и глэмпинга — только явно подписанные Mock-допущения; до интеграции нужно согласовать timezone, длительности и серверный DTO.
- Единица тарифа не подтверждена. UI не рассчитывает стоимость часа/ночи.
- Mock-данные не переживают полную перезагрузку и не являются настоящей авторизацией/бронью.
- API-режим собран, но не проверялся против запущенного Backend. Для ДЗ №5 необходимо отдельно проверить OpenAPI, серверное определение пользователя/статуса, `409 Conflict`, timeout и запрет автоматического повтора POST.
- В production-зависимостях остаётся critical advisory для текущего Next.js; обновление требует отдельной безопасной dependency-итерации на поддерживаемой Node 22 LTS с `npm ci`, сборками и regression-тестами.
- Риск исходного `/objects/page.tsx`, где ошибка могла превращаться в `null`, устранён для каталога в итерации 02, но единообразный аудит error-state остальных старых/admin-страниц ещё нужен.
