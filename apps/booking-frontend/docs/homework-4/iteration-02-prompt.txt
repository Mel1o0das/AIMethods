Цель текущей итерации
Реализовать редизайн главной / и каталога /objects на базе концепции №2 «Премиальный отдых». Главная должна вести к реально работающему каталогу, а каталог должен обеспечивать первый из трёх обязательных сценариев ДЗ №4: просмотр, поиск и фильтрацию Mock-объектов. Две другие функции (оформление и отмена бронирования) будут доведены до сквозных UI-сценариев в следующих итерациях.
Визуальные требования
1. Сохранить стиль концепции №2: тёмный хвойный/графитовый фон, тёплые песочно-золотистые акценты, выразительная типографика, атмосферный hero с изображением бани/домика, раздел «Коллекция мест»; на мобильном экране — одноколоночная вертикальная компоновка. Не копировать интерфейс побайтно; адаптировать к реальному BookingService и существующим компонентам.
2. Из концепций №1 и №3 использовать полезные функции, не меняя выбранную визуальную концепцию: удобный поиск/фильтры, цена, вместимость и чёткий CTA у карточки. Выбор даты/времени отложить до отдельного сквозного сценария; нельзя создавать неработающую форму поиска по датам и показывать якобы подтверждённую доступность.
3. Использовать src/app/page.tsx, src/app/objects/page.tsx, src/app/components/BookingObjects.tsx, AppHeader.tsx, уже существующие CSS-файлы либо небольшие специализированные компоненты. Сохранять Ant Design. Не использовать сторонние фреймворки без необходимости.
4. Фотографии брать из проверенных локальных ресурсов или существующих imageUrl у объектов; при отсутствии — качественная нейтральная заглушка. Не копировать фотографию из скриншота v0 и не добавлять непроверенные внешние hotlink-URL. Если отсутствует фотография для hero, реализовать стилистически подходящий CSS-фон с содержательной иллюстративной заглушкой и указать ограничение в отчёте.
5. Доработать общий header и footer ровно настолько, насколько нужно для визуального единства; не ломать /login, /register, /my-bookings, /admin, /admin/bookings, /objects/[id].
6. Обязательно проверить ширины 375, 390, 430, 768 и 1280 CSS px: без горизонтального скролла, удобные касания, доступные фильтры. Уважать prefers-reduced-motion, сохранять видимый фокус и разумный контраст.
Работающий каталог и состояния
7. Сохранить и использовать действующий интерфейс источника данных из итерации 01 (обёртки getObjectsPaged, getObjectTypes, data-source.ts). Не делать API-запросы напрямую из нового UI и не изменять DTO ради дизайна.
8. Сохранить текущие функции поиска, фильтрации по типу, максимальной цене, минимальной вместимости, сортировки и пагинации. При изменении фильтра переходить на первую страницу. На главной можно сделать простой поиск по названию/тексту с переходом в /objects?search=...; каталог должен корректно читать это значение. Если фильтры реализованы другим способом, согласуй и объясни техническое решение. Не выдавай поиск по дате за реализованный, если слой данных этого не поддерживает.
9. Устранить проблему исходного src/app/objects/page.tsx: пустые catch и .catch(() => null) не должны скрывать сбой. Должны существовать четыре различимых состояния: loading (загрузка), empty (действительно нет совпадений), error (не удалось загрузить данные, с кнопкой «Повторить»), success (карточки и пагинация). Ошибка получения типов не должна превращать каталог в ложное «нет объектов»; явно обработай её отдельно. При повторной загрузке не отображай устаревшие данные как новый успешный ответ.
10. Мобильные фильтры оформить как доступную панель/Drawer. Сохранить применённые значения при закрытии; дать действия «Применить» и «Сбросить». На десктопе фильтры видимы или легко доступны. Не терять параметры поиска при изменении сортировки/страницы.
11. Не подписывать поле price как «₽/час» или «₽/ночь», пока единица тарифа не подтверждена API. Если в Mock представлены условные суммы, дать неброскую явную пометку «Демонстрационные цены» / «Условная цена», сохранив ранее реализованный баннер Mock-режима.
12. Кнопка «Подробнее» должна вести на существующий /objects/[id]. Не удалять текущую функцию оформления из карточек. Если Mock-авторизация не готова, не изображать реальное успешное бронирование — ограничься работающей навигацией, а авторизацию и бронирование оставь следующему этапу.
13. Не добавлять фиктивные кнопки избранного, онлайн-оплаты или другие неработающие интерактивные элементы. Если элемент не реализуется, он должен быть явно декоративным и не выглядеть как рабочее действие.
Автоматические проверки и доказательства
14. Сохрани 5 существующих тестов из итерации 01. Добавь хотя бы 3 UI-проверки (Vitest + React Testing Library), желательно: (а) введённый поиск/фильтр меняет отображаемые Mock-результаты или передаваемые параметры; (б) пустая выборка показывает «Сбросить фильтры»; (в) отказ загрузки показывает отдельный error и «Повторить», после повторной попытки карточки появляются. Если из-за архитектуры проще разнести тесты по компонентам — допускается, но проверки должны исполняться и проверять поведение, а не наличие статической строки.

Границы изменений
- Не трогать Backend, PostgreSQL и реальные endpoints.
- Не переделывать в этой итерации форму BookingFormModal.tsx и список /my-bookings (кроме точечных исправлений, необходимых для совместимости).
- Не менять Mock/API переключатель, логику JWT или разрешения администратора без технической необходимости.
- Не запускать npm audit fix --force и не обновлять массово зависимости автоматически. По отчёту итерации 01 у зависимостей 18 уязвимостей, в том числе 3 critical: отдельно выполни диагностический npm audit --omit=dev (по возможности) и зафиксируй уязвимые runtime-пакеты, предложи план исправления без принудительных major upgrades. Это не должно блокировать дизайн, но не скрывай риск.
- Node.js 20.17.0 ниже ограничения eslint-visitor-keys@5.0.1 для ветки 20. Не исправляй это отключением проверки; рекомендуй подходящий Node, например актуальную 22 LTS, и повторную установку зависимостей при переходе версии.
